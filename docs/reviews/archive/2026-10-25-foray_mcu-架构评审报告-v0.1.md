### 2.2 分层：在 include 层是真实成立的【事实】

150 个项目自有文件共 492 条 `#include`。按目录类归并后：

| 依赖边 | 条数 | 判定 |
|---|---|---|
| Application → Platform `Interface/*.hpp` | 13 | 正当（唯一 App→Platform 通道） |
| Libraries → Platform `Interface/*.hpp` | 13 | 正当（Device 用契约） |
| **业务（App+Lib）→ Detail / Port / HAL / 寄存器** | **0** | **依赖倒置成立** |
| Interface → Detail | 7 | 三段式第一段 |
| Port → Detail | 12 | 三段式第三段 |
| Port → PortKit | 5 | Port 私有基础设施 |
| Port → CubeMX/Core 配置头 | 8 | 预期（Port 是唯一碰厂商处） |
| CubeMX 生成区 → Application | 2 | **破口**：`main.c:37`、`freertos.c:29` include `Application/Entry.h` |
| CubeMX 生成区 → Port 私有头 | 1 | `main.c:38` include `Init.h` |
| USB 生成区 → Port 私有头 | 2 | **破口**（UsbCdc） |
| Application/Task → RTOS | 4 文件 | 任务层豁免，但与契约层级混杂 |

结论：**业务只依赖 Interface 契约，Interface 零 HAL、零 RTOS；Port 只依赖 Detail + PortKit + CubeMX。这个分层纪律是真实存在的资产，重构必须继承而不是重写。**

### 2.3 三段式契约：成立，但有三处缺口

- 第一段 `C++ 门面 .hpp → Detail C ABI`：成立。7 个 `.hpp` 各只 include 自己的 `Detail/*.h` 加标准库；业务代码 0 处直接调用 `CanPort_*` 等 C ABI。
- 第二段 `Detail`：只依赖 `stdint/stdbool`；MUST/MAY 能力分级注释存在（6/7 个 Detail 头，`Pwm.h` 缺说明块）。
- 第三段 `Port C11`：只有 `Detail + PortKit + CubeMX`，零 RTOS 调用。

**缺口 1：MAY 是注释级契约，没有执行机制，且已被违反。** `SPI` 异步三个函数标为 MAY，但 BMI088 / WS2812 把它们当 MUST 使用且无 `Unsupported` 回退（`Bmi088Accel.cpp:183-201`、`Ws2812.cpp:100-125`）。F407 若用阻塞 SPI 实现，"可选能力"会让 IMU 驱动进入故障态。
**缺口 2：UsbCdc 是唯一三段式失效的子系统。** `Port/UsbCdc.c` include 生成 USB 栈、`extern hUsbDeviceHS`、实现 `__wrap_HAL_PCD_EP_Transmit`（链接器 `--wrap`）；反过来 USB 生成代码 `usb_device.c` / `usbd_cdc_if.c` 调 `UsbCdcPort_*` 私有 ABI（声明只在 `Port/UsbCdc.h`）。而 `Interface/UsbCdc.hpp` 在业务中**零消费者**——实际接口是 Port 私有头。
**缺口 3：能力枚举双份硬编码、无 ABI 版本。** Interface 与 Detail 各写一份：CAN 3 通道、SPI 3 设备、UART 2 端点、PWM 2 通道、GPIO 8 脚；结构体跨 C/C++ 边界传值无 `sizeof`/version 校验。

### 2.4 构建系统：没有"层"【事实】

- 单 executable `mc02_cpp`（`Platform/STM32H7/DM_MC02/CMakeLists.txt:39`）；`file(GLOB_RECURSE)` 把 `Port/*`、`Application/*`、`Libraries/{Algorithm,Component,Device,Protocol}/*` 全部塞进去（:89-102）。
- 真实 target 只有 `platform_interface`（INTERFACE）、`portkit`（OBJECT）与 CubeMX 的三个 OBJECT 库；**Port 不是 target**。
- 全仓 include 根是仓库根（:115-120）；业务同时依赖两个 include 根（裸头名 `"Can.hpp"` 与全路径 `"Platform/Interface/Time.hpp"` 混用）。
- `-Wextra -Werror` 只覆盖 `PROJECT_SOURCES`（实测 65 个编译单元中 44 个）。
- 无 `enable_testing`/`add_test`；无板/兵种维度；产物名固定。
- `CMakePresets.json:11-19` 硬编码 `C:/Users/pomelo/...`；flash 目标引用的 `openocd/stm32h723_stlink.cfg` 不存在，且 `*.cfg` 被 `.gitignore:8` 忽略 → 干净 clone 下不会生成 flash 目标（configure 仅打印一条 STATUS）。
- CubeMX 生成的 `cmake/stm32cubemx/CMakeLists.txt` 每次再生成会改写源列表与 include 路径；顶层板 CMakeLists 只生成一次（可手改）。

**结论：目录再漂亮，只要还是"单 executable + GLOB + 全仓 include"，层就没有构建期约束，重构收益接近零。**

### 2.6 多板、RTOS 与契约的硬限制【事实/推断】

- **只有一块板**：`Platform/STM32H7/DM_MC02/` 是唯一构建目标；架构图与组织对齐分支 README 提到的 F407/RM_Cboard，在当前树中不存在（空目录也未入 git）。多板目前是"图上的承诺"。
- **契约枚举是本机器人能力集**（见 §2.3 缺口 3）：换一块少一路 CAN、没有 IMU 加热或 LED 的板，要么改公共契约头（污染），要么每板一份契约（app 绑板）。
- **PortKit 绑 Cortex-M**：`PortKit.c:2` include `cmsis_compiler.h`，临界区用 `PRIMASK` 全局关中断；而 FreeRTOS 配置用 BASEPRI 掩码（`FreeRTOSConfig.h:145-152`），两者嵌套语义不一致。TI 复用不可直接搬。
- **时基绑 DWT**：`Port/Time.c:36-60` 用 Cortex-M7 DWT/CYCCNT；`ZeroRateBiasObserver.hpp:41` 默认 tick 频率硬编码 480 MHz。
- **RTOS 双栈混用**：任务层同时用 `cmsis_os2` 与 FreeRTOS 原生 `uxTaskGetStackHighWaterMark`（`TaskManager.cpp:8,211`），无 OS 抽象层。
- **启动权在生成区**：`main.c:134-141` 调 `Port_Init`/`Application_Init`；`freertos.c:114` 调 `Application_InitRtos`；`freertos.c:139-143` 每 1 ms 调 `Application_Start`。换板 = 重接生成文件。
- **CMSIS-DSP 链接但未使用**：工程链接 `arm_cortexM7lfsp_math`，但项目代码无 `arm_*` 引用，`.map` 中无相应符号（仅 archive 载入行）→ 可移除。

## 3. 对提案的拆解与判定

### 3.1 提案原文（评审对象）

> app 做业务层，按兵种划分，后续可通过 cmake 快速切换编译；config 为装配根，按机器人划分，根据不同的兵种所具有的能力分配，被 app 所依赖。platform 为平台层，按厂商和开发板分，存放 cubemx 生成文件和手写的能力适配层。src 则为一个通用框架，里面存放公共的 bsp 层，被内部的 driver 等调用，还有 topic 架构以及一些算法库、小组件等。另有 test、tool、docs。

### 3.2 逐目录职责判定

| 目录 | 应回答的问题 | MUST 依赖 | MUST NOT 依赖 |
|---|---|---|---|
| `app/` | 一类**能力/行为**怎么实现（imu/chassis/gimbal/remote/link/launch） | `src` 的契约与公共库；本层 `app/common` | `platform` 实现/生成区；`config/assembly`；其他能力的内部实现（跨能力只经 msg/契约） |
| `config/` | 一台**具体机器人**用哪些能力、什么参数、装在哪块板 | `app`（assembly 链接）；`platform/board`（板能力） | 实现算法/协议/驱动；`profile` 不得 include 任何代码头 |
| `platform/` | 某块板如何把 C ABI 落到 HAL/寄存器；CubeMX 生成了什么 | `src/hal/abi`、`src/hal/os` 契约；厂商 HAL/FreeRTOS/USB/CMSIS | `app`、`config` 的任何头（boot 契约除外）；把 HAL 类型放入公共头 |
| `src/` | 与产品和板都无关的通用框架（契约/算法/设备/消息） | 层内白名单（见 §5.7）；标准库 | `platform`、`app`、`config`、RTOS/HAL 头（`hal/os` 契约除外） |
| `test/` | 契约与行为是否可脱离硬件验证 | 被测 target + `platform/mock` + ctest | 真实 port/生成区；**不得进入固件链接图** |
| `tool/` | 烧录/调试/生成/检查怎么做 | 无构建期依赖 | 不得成为固件构建的必需步骤；不得被 gitignore |
| `docs/` | 分层判据、决策、证据链 | 无 | 不得与代码/CI 规则不一致 |

### 3.3 必须修正的四处边界

#### M1 `config` 的双重身份会造成构建环

- **问题**：提案同时要求"`config` 是装配根"（要链接 `app`）与"`config` 被 `app` 依赖"（`app` 要 include `config`）。在 CMake target 依赖图上，同一 target 既被 `app` 依赖又依赖 `app` ⇒ **环**；实际表现是 configure 阶段依赖图错误，或被迫用 INTERFACE/OBJECT 绕成"看起来能编"的隐式环。
- **后果**：`app` 无法在没有机器人配置时单独编译/宿主测试；配置与实现的单一真源被破坏；换 profile 时无法判断改哪一边。
- **建议规则**：把 `config` 拆成两个 target：
  - `foray_profile_<profile>`：**INTERFACE 叶子**，只含生成头（能力集合、参数常量、板卡 ID），不 link 任何 target；
  - `foray_assembly_<profile>`：**STATIC 组合根**（`config/assembly/`），负责任务表、对象构造、启动入口、参数注入，只被最终 executable link；
  - `app` 只依赖 `foray_profile`（若允许）或完全不依赖 profile（推荐：参数由 assembly 注入）；`app` **绝不**依赖 assembly。
- **验收**：`cmake --graphviz` 生成的 target 图中不存在经过 `app → profile → assembly → app` 的环；把任意一个 profile 换成 `test_profile`，`app` 与 `src` 的源码零改动即可编译。

#### M2 `app` 按兵种划分会导致复制分叉

- **事实**：现有 `Application/` 实际上就是按**能力**长的（`Task/0_imu`、`1_chassis`、`2_gimbal`、`4_communication`），兵种差异并不存在于代码结构；真正"换车必改"的只有 4 个文件（§2.5）。兵种间共享 IMU 姿态估计、云台模块、底盘控制器等大部分代码。
- **后果**：按 `app/infantry`、`app/hero` 建目录后，同一能力必然出现多份副本：一个 bug 要修 N 份、参数/接口漂移、review 无法判断哪份权威；config 的"能力分配"也失去意义（因为代码已经按兵种复制了）。
- **建议规则**：
  - `app` 一级目录使用**能力/角色白名单**（imu/chassis/gimbal/remote/link/launch/common/tasks/debug_comm）；
  - **兵种（branch）是 profile 的属性，机器人（robot）是 profile 实例**；新兵种 = 既有能力的重新组合 + 参数差异；新行为 = 新增 capability，而不是复制目录；
  - 能力用**链接期 target 组合**表达：每个能力一个 STATIC 库，`assembly` 按 profile 的能力列表 `target_link_libraries`；禁止 `#if FORAY_*` 出现在 `app/src`，禁止 `includes.h + USE_XXX` 宏开关模式（RM 社区已有反面案例）。
- **验收**：新增一个兵种 profile 时 `git diff --stat` 只触及 `config/profiles/`（+ 需要时一个 preset）；CI 检查 `app` 一级目录 ∈ 白名单。

#### M3 `src/bsp` 一词两义，且契约少了 C ABI 一半

- **事实**：`src/bsp/hardware/` 下 7 个占位 `.hpp` 与现有 `Platform/Interface/*.hpp` 一一对应；但现有契约能支撑宿主测试的关键是 `Platform/Interface/Detail/*.h`（纯 C11 ABI），骨架中没有对应位置。传统 BSP = Board Support Package（板级实现），而提案又用 `platform/*/bsp_impl` 表示手写实现——同一个词同时指契约与实现。
- **后果**：①名称歧义会长期消耗评审时间；②只搬 `.hpp` 不搬 `Detail`，宿主测试无法再桩 C ABI，mock 平台无从实现；③`bsp` 目录容易变成"什么都往里放"的垃圾桶；④PortKit（CMSIS/PRIMASK）若被当作"公共框架"搬进 src，会污染平台无关层。
- **建议规则**：
  - `src/hal/`：C++ 门面契约（`can.hpp … usb_cdc.hpp`）+ `src/hal/abi/`（C ABI，对应现有 `Detail/*.h`）+ `src/hal/os/`（线程/延时/临界区契约，可选）；
  - `src/boot/`：启动 ABI（见 M4）；
  - `platform/<vendor>/<mcu>/<board>/` 拆 `cubemx/`（生成物）、`port/`（手写 C11 实现）、`board/`（pinmap、时钟、能力清单、bring-up）；
  - `bsp` 一词只保留给 `platform/*/board/`（若保留），不再出现在 src；PortKit 的队列/通知进 `src/utils/`，临界区契约进 `src/hal/os/`，其 CMSIS 实现留在 platform。
- **验收**：`grep -r "Detail/"` 只在 `src/hal` 内；宿主测试只链接 `src/hal`/`src/lib`/`platform/mock` 即可编过；`src/**` 中 grep 不到 `cmsis`、`HAL_`、`FreeRTOS`、`stm32`。

#### M4 CubeMX 生成区已破界 + 平台契约是"本机器人能力集"

- **事实 A（生成区破界）**：`Core/Src/main.c:37` 与 `Core/Src/freertos.c:29` include `Application/Entry.h`，并在 USER CODE 区调 `Application_Init/InitRtos/Start`；`defaultTask` 承载应用周期。生成区与手写区在物理上同目录，靠 USER CODE 区与人工纪律维持。
- **事实 B（应收集的第二个破口）**：UsbCdc 生成代码与 Port 私有 ABI 双向直连（§2.3 缺口 2），不能按"接口/实现"直接切。
- **事实 C（能力枚举）**：`Gpio::Pin`（Power24V1/Power5V/UserKey/IMU CS/INT）、`Spi::Device`（ImuAccelerometer/ImuGyroscope/AddressableLed）、`Uart::Endpoint`（RemoteReceiver/DebugConsole）、`Pwm::Channel`（Buzzer/ImuHeater）、CAN 固定 3 通道——都是 DM_MC02 的逻辑资源；Interface 与 Detail 双份写死。原样搬进 `src` 共享契约后，F407/TI 只有两条路：设备并集污染，或每板一份契约使 app 绑板。
- **建议规则**：
  1. `platform/**/cubemx/**` 只放生成物（Core/Drivers/Middlewares/USB_DEVICE/*.ioc/startup/.ld），手写代码 0 个；`port/`、`board/` 在物理上分开；CODEOWNERS + CI regenerate-diff（或生成清单 sha256）保证再生成不覆盖手写。
  2. 引入 **boot ABI**：`src/boot/foray_boot.h` 声明纯 C 的 `ForayBoot_Init / ForayBoot_InitRtos / ForayBoot_Start`；生成文件只调这三个符号（实现落在 `config/assembly` 或 `platform/*/board`），**不再 include app 头**。
  3. **板能力清单**：`platform/*/board/board.cmake`（或生成头）声明该板"提供哪些能力/资源"；profile 声明机器人"需要哪些能力"；configure 期校验 `robot_requires ⊆ board_provides`，缺失即失败（而不是靠运行期 `IsReady` 糊过去）。
  4. **契约分两层**：`src/hal` 只保留通用总线/时基/存储等资源型契约（不枚举板级逻辑设备）；板级逻辑资源由 `platform/*/board` 声明、port 映射；若驱动需要绑定具体实例，在 `config/assembly` 装配期完成。
  5. UsbCdc 重划边界：把 `usbd_cdc_if` 归入 board 层，或把 UsbCdc 降为 board-private 能力，或改用 HAL 回调注册替代 `--wrap`；不允许继续"生成栈 ↔ Port 私有 ABI"双向直连。
- **验收**：删除/替换任一生成文件后，`git grep "Application/" platform/**/cubemx` 为空；一个"空 app"骨架（只有 boot ABI）可单独构建并点亮板；换一块能力更少的 mock 板时 configure 期能报出缺失能力。

### 3.4 提案缺失的必需物

1. **根 CMake 与 presets**：当前骨架没有任何构建文件；没有 root target 模型就没有"层"。
2. **宿主测试 + `platform/mock`**：契约层的可替换性必须能被验证；历史 Tests 可从 `fd1edbb` 恢复。
3. **CI 架构门禁**：include/依赖方向、生成区、禁止 GLOB、vendor 哈希、手写协议检查；规则不机器化必然回潮。
4. **`src/boot`、`src/third_party`、`platform/mock`、板能力清单**：分别对应启动接缝、foray_interfaces 生成头、宿主可测性、多板能力校验。
5. **组织合规件**：`.foray-layer`、`CODEOWNERS`、CI（与五件套一起构成仓库规范）。

### 3.5 提案中正确的部分（先说优点）

- 四块切分与"装配根"直觉正确，直接命中现有"装配知识分散 + 生成区破界 + 构建无边界 + 测试缺失"四个痛点。
- `platform` 按厂商/开发板分层并物理隔离生成区，是解决 CubeMX 再生成与多板复用的正确方向。
- `src` 收拢通用框架（含算法、组件、topic）符合"可宿主编译、跨产品复用"的目标。
- `test/tool/docs` 一级化，正确对应"测试/工具/证据链必须入库"的教训。
- 与行业实践一致：Zephyr 的 board/SoC/driver 分离、ESP-IDF 的组件 PRIVATE/PUBLIC 依赖、XRobot 的"配置生成装配代码"都印证了同一方向。

## 5. 推荐目标结构与构建模型

### 5.1 目标目录

完整目录见 [tree.md](../../tree.md)。核心变化（相对当前骨架）：

- `src/bsp/hardware` → `src/hal`（+ `abi/`、`os/`）；新增 `src/boot/`、`src/third_party/`；
- `platform/st/board_dm/bsp_impl` → `platform/st/stm32h7/board_dm/{cubemx,port,board}`；platform 增加 MCU 层（H7/F4）与 `mock/`；
- `config` 拆 `profiles/<robot>/`（纯数据）与 `assembly/`（组合根）；
- `app` 按能力拆分（不按兵种）；
- `test/` 分 `host/{unit,integration}`、`hil/`、`data/`；`tool/` 分 `flash/debug/ci`。

### 5.2 CMake target 依赖图（目标态）

```text
EXECUTABLE  foray_firmware_<profile>
 ├─ STATIC       foray_assembly_<profile>        config/assembly（组合根：任务表/对象构造/boot 实现）
 │   ├─ INTERFACE foray_profile_<profile>        config/profiles（纯数据生成头，叶子，无依赖）
 │   ├─ STATIC    foray_app_<capability>         app/<capability>（可选集合由 profile 决定）
 │   │   ├─ INTERFACE foray_app_common
 │   │   ├─ STATIC    foray_msg
 │   │   ├─ STATIC    foray_driver_<device>      src/driver
 │   │   │   ├─ INTERFACE foray_hal              src/hal（C++ 契约）
 │   │   │   │   └─ INTERFACE foray_hal_abi      src/hal/abi（纯 C11）
 │   │   │   └─ STATIC    foray_lib_<pkg>        src/lib（纯算法/组件，零平台）
 │   │   └─ STATIC    foray_middleware_<svc>
 │   └─ STATIC    foray_board_<board>            platform/<vendor>/<mcu>/<board>/board
 └─ STATIC       foray_port_<board>              platform/.../port（实现 C ABI；PRIVATE 依赖 vendor）
     ├─ OBJECT   mx_generated_<board>            cubemx/ 生成物（Core/USB_DEVICE/Middlewares）
     ├─ OBJECT   freertos_<board>
     └─ OBJECT   usb_device_<board>

宿主测试（不交叉编译）：
EXECUTABLE foray_test_<name>  →  被测 target + STATIC foray_platform_mock + ctest
```

### 5.3 依赖规则（建议纳入 CI，机器可验）

1. `app` 不得 link/看见 `foray_port_*`、`foray_board_*`、`mx_generated_*`、`freertos_*`、`foray_assembly_*`。
2. `src` 任何 target 不得依赖 `platform`/`app`/`config`；`src` 必须能只靠 `platform/mock` 在宿主机构建。
3. `src/hal` 不得出现 `stm32`、`cmsis`、`HAL_`、`FreeRTOS`、`cmsis_os2`；`src/hal/abi` 只允许 `stdint/stdbool/stddef`。
4. `config/profiles/**` 不得 include 任何工程头；`profile` 是叶子。
5. `foray_assembly_*` 是组合根，任何 target 不得 link 它；任何头不得被 assembly 之外的 target include。
6. `test` 不得 link `foray_port_*`/`foray_board_*`/`foray_assembly_*` 的真实实现；测试二进制不得进入固件链接图。
7. `platform/**/cubemx/**` 不得出现 `app/`、`config/`、`Application/` 的 include；只允许 boot/board 契约头。
8. 禁止 `file(GLOB)` 收集业务源码；禁止全局 `include_directories()`；每 target 用 PRIVATE/PUBLIC/INTERFACE 显式声明。
9. `app/src` 中禁止 `#if.*FORAY_`（能力裁剪用 target 组合）；`#if` 只允许出现在生成头与 platform 适配层。
10. 只有任务外壳/`app/common` 允许 `#include <cmsis_os2.h>`（迁移期），终态只允许 `src/hal/os/*`；`src/lib`、`src/driver` 零 RTOS。
11. 链路协议只允许来自 vendored `lower_link.hpp`（版本 + sha256 固定）；禁止在 `app/src` 出现手写帧/CRC。
12. `app` 一级目录白名单、`src` 一级目录白名单、`platform` 一级目录白名单；新增需 `decision.md` 登记。

### 5.4 唯一开关与 presets 矩阵

- **唯一命令行开关：`-DFORAY_PROFILE=<name>`**；板卡、能力集合、参数全部来自 `config/profiles/<name>/profile.cmake`。
- 常用 preset：`arm-debug`（默认 profile × board_dm × Debug）、`arm-release`、`host-tests`；其他兵种/板在 CI 用显式 `-B` 目录展开（`cmake --preset` 的 binaryDir 不能引用 cache 变量，不要试图一个 preset 打天下）。
- 工具链进 `cmake/toolchains/{arm-gcc-cortex-m7,arm-gcc-cortex-m4f,host}.cmake`；本机路径进 `CMakeUserPresets.json`（不入库），CI 用环境变量。
- 生成 `foray_profile.hpp`（能力常量 + profile id + 源文件 hash + git describe），供装配/诊断/测试断言；app 不直接 include。
- 能力常量用 `constexpr` 而非宏；能力开关不生成 `#define FORAY_CAP_*`，而是决定 assembly 链接哪些能力库。

### 5.5 能力模型

- **机器人需求 vs 板能力**：`config/profiles/<robot>` 声明 `FORAY_FEATURES`（能力集合）；`platform/.../board/board.cmake` 声明 `BOARD_PROVIDES`（该板能提供的总线/设备/资源）；configure 期校验 `robot_requires ⊆ board_provides`。
- **能力 = target**：`foray_app_<capability>`；assembly 只链接 profile 列出的能力。未链接的能力不会进镜像（含其全局对象），也不存在"编进来但未启用"的组合。
- **模块内差异**：用 `constexpr bool` / 依赖注入 / 接口多态（非虚函数优先）表达，不用预处理分支。
- **新兵种**：既有能力重组合 + profile 参数；**新行为**才新增 capability 库。新板才新增 platform board。

### 5.6 启动接缝与生成区隔离

- `src/boot/foray_boot.h`：纯 C 的 `ForayBoot_Init / ForayBoot_InitRtos / ForayBoot_Start`。
- CubeMX 生成文件的 USER CODE 区只调用这三个符号（`main.c` 的 USER CODE 2、`freertos.c` 的 RTOS_THREADS、defaultTask 循环体各一处）；生成文件不再 include app 头。
- `--wrap=HAL_PCD_EP_Transmit` 等链接技巧保留，但登记为"生成区 seam 例外"，后续改为回调注册。
- 生成区治理：`cubemx/` 只允许由 CubeMX 产生；CODEOWNERS 单独 review；CI 用 regenerate-diff（有 CubeMX 的 runner）或 `generated.manifest`（sha256 清单）校验。

### 5.7 `src` 层内 DAG、topic 与 OS 抽象

- **层内单向**：`utils ← lib(算法/组件) ← driver(设备/设备协议) ← msg/middleware ← hal(契约)`。`lib` 不碰 OS/driver/msg；`driver` 只碰 `hal`/`lib`；`msg` 不依赖 `driver`。
- **先把既有债裁决掉**：`ImuBodyMapping` 的 Device 反向依赖（改成 POD 入参或迁到 `src/driver/imu/`）、Device→Algorithm/Protocol 的合法下行依赖写入文档；否则搬进 src 只是复制债务。
- **topic 第一版不引入**：先 1:1 搬迁 + 恢复测试。最小 topic 规范：固定 POD、静态表、编译期 ID、`Peek()`（零拷贝，接受覆盖语义）与 `Take()`（拷贝）分离、ISR 只 publish、每 topic pub/drop 计数、禁止总线级 RPC、禁止运行时自动发现。1 kHz 控制 + 500–625 µs IMU 的实时预算需先在纸面算清。
- **OS 抽象暂不建**：当前只有 FreeRTOS 且任务层双栈混用；若 TI 侧也用 FreeRTOS，`src/hal/os` 是纯成本。先保留"RTOS 只出现在任务/装配层"的规则；PortKit 的队列/通知留在 platform/utils 侧。

## 7. 迁移方案

### 7.1 原则

1. 先有可对照的基线（构建 + 测试），再搬目录；**搬迁不改行为**。
2. 每个阶段可构建、可回滚、有量化对照（`.bin`/`.map`/`ctest`）。
3. 结构迁移与"丢失进度恢复"分开立项。
4. 保留 git 历史与 `git log --follow`；不空目录重写。

### 7.2 阶段、动作、验收、回滚

| 阶段 | 动作 | 验收 | 回滚 |
|---|---|---|---|
| **P0 基线与资产**（0.5–1 天） | 迁入 ControllerCode git 历史；从 `fd1edbb` 恢复 Tests；清理 `.gitignore`；复现基线构建；补齐 `.foray-layer`/CODEOWNERS/CI 第一版；确认基线 | `ctest` 绿；基线 `.bin` 238,320 / 100,664 B 与 SHA 记录在 docs；`git log --follow` 可用 | 删除分支/回到空仓，不留半成品 |
| **P1 构建骨架**（1–2 天） | 根 CMake/presets；`src/hal`+`abi`、platform/mock、最小 host test；顶层 executable 统一链接；每 target 私有 include | **零源码改动**下 `.bin` 与基线一致（或段大小/map 符号集一致）；ctest 可跑；graphviz 与 §5.2 一致 | revert 单提交 |
| **P2 纯搬迁**（1–2 天） | `git mv` + include 机械改写；拆 cubemx/port/board；删除根 include 与 GLOB | 构建绿；`.bin`/`.map` 对照；`git diff -M` 为纯 rename + include；ctest 绿 | revert P2 分支 |
| **P3 装配根/能力拆分**（2–4 周） | 拆 profile/assembly；能力 target；修既有结构债（ImuBodyMapping、Imu 域例外、defaultTask、periodMs、死端点、DjiMotorModelMap） | ≥2 profile × 1 板构建；host test 绿；CI 分层检查绿；体积 ≤ 基线 +5%；行为对照 | 按能力 PR revert |
| **P4 协议/多板/CI 矩阵** | vendored lower_link + link 任务；安全硬路径；F4 板；TI 评估；CI 全矩阵；tool/docs 证据链 | 每板产物；链路测试绿；实机回归清单；组织 CI 绿 | 分项 revert |

### 7.4 git 与 .gitignore

- 建议在 `foray_mcu` 内建仓并把 ControllerCode 作为 remote/legacy 取历史（或直接把 ControllerCode 重命名迁入）；首个 tag `baseline/a2cfd16`。

### 7.5 与"丢失进度恢复"的关系

见 §1.4。**先确认基线**；若存在比 `a2cfd16` 更新的完整代码，先收编/打 tag 再迁移；若最新进度确实丢失，按 ControllerCode 的《固件恢复可行性评估》单独推进恢复，不与结构迁移混做（否则"重构后行为变化"无法区分是结构问题还是恢复缺失）。

### 附录 E：术语

| 术语 | 含义 |
|---|---|
| 装配根 / 组合根（composition root） | 唯一组装对象图与启动顺序的位置；本项目落在 `config/assembly` + 顶层 executable |
| 能力（capability） | 可复用的行为/设备角色（imu、chassis、gimbal…）；用 target 表达 |
| profile | 一台机器人/兵种实例的纯数据描述（能力集合、参数、板卡） |
| 板能力清单（board manifest） | 某块板能提供的总线/设备/资源；与 profile 的需求做 configure 期校验 |
| BSP | Board Support Package（板级实现）；本项目建议只用于 `platform/*/board`，契约层用 `hal` |
| 依赖倒置 | 业务依赖抽象契约，平台实现契约；本项目三段式：C++ 门面 → C ABI → Port C11 |
| 架构门禁（architecture gate/fitness function） | CI 里可执行的架构规则：依赖图、include 白名单、生成区、禁 GLOB 等 |
| SPL / 产品线工程 | Software Product Line：用共享资产 + 受控变体点构建一族产品 |
