## 0. 摘要（给时间有限的评审人）

| 问题 | 结论 |
|---|---|
| 提案方向是否正确？ | **是**。`app / config / platform / src / test / tool / docs` 的切分符合"平台 + 产品线 + 装配根（=组合根）"的通用做法，且与现有代码已有的分层哲学连续。 |
| 能否按当前骨架直接开工？ | **否**。当前只是目录草图：无根 CMake、无 target 边界、无 mock/host 测试、无 CI；`src/bsp` 下只有 7 个 0 字节的 C++ 占位头（v0.4：契约本来就应该是 C++ 头，见 §5.11）。 |

### 1.4 重要前提：迁移基线不唯一（本方案最大前置风险）

【事实】

1. 当前 clone 的 `main` @ `a2cfd16` 不包含架构图附录 A/B 所描述的更新代码：图里出现 `RemoteControlTask`、`ChassisModule`、`RemoteControlModule`、`GimbalStabilizationController`、`DebugComm`、`damiao`、`robolink`、`LatestValueMailbox`、20 个测试子工程与 `Tools/` 脚本，而当前树中没有这些文件。
2. 当前树的业务链是断的：`ChassisTask::SetWheelTarget`、`GimbalTask::SetGimbalTarget`、`RemoteReceiver::GetSnapshot`、`AttitudeEstimator::GetOutput` 的**外部调用者均为 0**；`Application/Task/4_communication` 没有独立线程；遥控解析寄生在 CubeMX 生成的 `defaultTask` 每 1 ms 轮询里（`Core/Src/freertos.c:139-143`）。
3. 架构图标注的代码实测日期是 2026-10-22；`a2cfd16` 的提交时间是 2026-10-22 23:17 −0400（即 2026-10-23 11:17 +08），两者基本是同一天，时间先后本身**不是有力证据**【v0.3 校正】。真正的证据是第 1 点：图中描述的文件在当前树中不存在——说明图基于另一份工作树（或更完整的代码状态），不能直接与 `a2cfd16` 对齐。

【推断】存在两种可能：①`a2cfd16` 是恢复过程中被裁剪过的基线；②最新进度在另一份代码/机器上且尚未进入本 clone。无论哪种，**"用哪份代码作为迁移基线"必须先定**：结构迁移与"丢失进度恢复"是两条线，混在一起会导致基线不可控、回归无法对照。

### 2.2 分层：在 include 层是真实成立的【事实】

150 个项目自有代码文件共 492 条 `#include`。按目录类归并后：

| 依赖边 | 条数 | 判定 |
|---|---|---|
| Application → Platform `Interface/*.hpp` | 13 | 正当（唯一 App→Platform 通道） |
| Libraries → Platform `Interface/*.hpp` | 13 | 正当（Device 用契约） |
| **业务（App+Lib）→ Detail / Port / HAL / 寄存器** | **0** | **依赖倒置成立** |

| Port → Detail | 12 | 三段式第三段 |
| Port → PortKit | 5 | Port 私有基础设施 |
| Port → CubeMX/Core 配置头 | 8 | 预期（Port 是唯一碰厂商处） |
| CubeMX 生成区 → Application | 2 | **破口**：`main.c:37`、`freertos.c:29` include `Application/Entry.h` |
| CubeMX 生成区 → Port 私有头 | 1 | `main.c:38` include `Init.h` |
| USB 生成区 → Port 私有头 | 2 | **破口**（UsbCdc） |
| Application/Task → RTOS | 4 文件 | 任务层豁免，但与契约层级混杂 |

结论：**业务只依赖 Interface 契约，Interface 零 HAL、零 RTOS；Port 只依赖 Detail + PortKit + CubeMX。这个分层纪律是真实存在的资产，重构必须继承而不是重写。**

### 2.3 三段式契约：成立，但有三处缺口

- 第一段 `C++ 门面 .hpp → Detail C ABI`：成立。7 个 `.hpp` 各只 include 自己的 `Detail/*.h` 加标准库；业务代码 0 处直接调用 `CanPort_*` 等 C ABI。
- 第二段 `Detail`：只依赖 `stdint/stdbool`；MUST/MAY 能力分级注释存在（6/7 个 Detail 头，`Pwm.h` 缺说明块）。
- 第三段 `Port C11`：只有 `Detail + PortKit + CubeMX`，零 RTOS 调用。

**缺口 1：MAY 是注释级契约，没有执行机制，且已被违反。** `SPI` 异步三个函数标为 MAY，但 BMI088 / WS2812 把它们当 MUST 使用且无 `Unsupported` 回退（`Bmi088Accel.cpp:183-201`、`Ws2812.cpp:100-125`）。F407 若用阻塞 SPI 实现，"可选能力"会让 IMU 驱动进入故障态。
**缺口 2：UsbCdc 是唯一三段式失效的子系统。** `Port/UsbCdc.c` include 生成 USB 栈、`extern hUsbDeviceHS`、实现 `__wrap_HAL_PCD_EP_Transmit`（链接器 `--wrap`）；反过来 USB 生成代码 `usb_device.c` / `usbd_cdc_if.c` 调 `UsbCdcPort_*` 私有 ABI（声明只在 `Port/UsbCdc.h`）。而 `Interface/UsbCdc.hpp` 在业务中**零消费者**——实际接口是 Port 私有头。边界方案见 Q8。
**缺口 3：能力枚举双份硬编码、无 ABI 版本。** Interface 与 Detail 各写一份：CAN 3 通道、SPI 3 设备、UART 2 端点、PWM 2 通道、GPIO 8 脚；结构体跨 C/C++ 边界传值无 `sizeof`/version 校验。【v0.4】这处缺口是 C ABI 层本身带来的（例如 `Can.hpp:19` 的 `Channel1 = CAN_PORT_CHANNEL_1` 对应 `Detail/Can.h:28` 的又一份定义），契约统一用 C++ 后自然消失，见 §5.11。

### 2.4 构建系统：没有"层"【事实】

- 单 executable `mc02_cpp`（`Platform/STM32H7/DM_MC02/CMakeLists.txt:39`）；`file(GLOB_RECURSE)` 把 `Port/*`、`Application/*`、`Libraries/{Algorithm,Component,Device,Protocol}/*` 全部塞进去（:89-102）。
- 真实 target 只有 `platform_interface`（INTERFACE）、`portkit`（OBJECT）与 CubeMX 的三个 OBJECT 库；**Port 不是 target**。
- 全仓 include 根是仓库根（:115-120）；业务同时依赖两个 include 根（裸头名 `"Can.hpp"` 与全路径 `"Platform/Interface/Time.hpp"` 混用）。
- `-Wextra -Werror` 只覆盖 `PROJECT_SOURCES`（44 个项目业务 TU；编译数据库共 112 个 TU）。
- 无 `enable_testing`/`add_test`；无板/兵种维度；产物名固定。
- `CMakePresets.json:11-19` 硬编码本机路径 `C:/Users/<user>/...`；flash 目标引用的 `openocd/stm32h723_stlink.cfg` 不存在，且 `*.cfg` 被 `.gitignore:8` 忽略 → 干净 clone 下不会生成 flash 目标（configure 仅打印一条 STATUS）。
- CubeMX 生成的 `cmake/stm32cubemx/CMakeLists.txt` 每次再生成会改写源列表（:31-45）与 include 路径（:13-28）、target 定义（:126-147）；顶层板 CMakeLists 只生成一次（可手改）。
- **已有可继承的构建期防护（v0.3 补充）**：板级 CMakeLists 在 configure 期检查 CubeMX 再生成后 USB OTG HS 内部 DMA 仍开启、UsbCdc Port 仍含 PA11/PA12 复用配置（`:56-69`），这是现成的"生成区防回退"资产，迁移时保留。另有两个构建期开关 `IMU_ENABLE_DIAGNOSTICS`（`:40`）与 `IMU_GYRO_BANDWIDTH`（`:43-51`），P3b 收进 profile。

**结论：目录再漂亮，只要还是"单 executable + GLOB + 全仓 include"，层就没有构建期约束，重构收益接近零。**

### 2.6 多板、RTOS 与契约的硬限制【事实/推断】

- **只有一块板**：`Platform/STM32H7/DM_MC02/` 是唯一构建目标；架构图与组织对齐分支 README 提到的 F407/RM_Cboard，在当前树中不存在（空目录也未入 git）。多板目前是"图上的承诺"。
- **契约枚举是本机器人能力集**（见 §2.3 缺口 3）：换一块少一路 CAN、没有 IMU 加热或 LED 的板，要么改公共契约头（污染），要么每板一份契约（app 绑板）。
- **PortKit 绑 Cortex-M**：`PortKit.c:2` include `cmsis_compiler.h`，临界区用 `PRIMASK` 全局关中断（`:105-115`：进入时保存、退出时恢复原值，**嵌套是安全的**）；FreeRTOS 配置用 BASEPRI 掩码（`FreeRTOSConfig.h:145-152`）。两者并不冲突，区别只是 PRIMASK 会屏蔽所有中断（包括优先级高于 `configMAX_SYSCALL_INTERRUPT_PRIORITY` 的中断），代价是中断延迟。【v0.3 校正：v0.1/v0.2 写的"两者嵌套语义不一致"不准确】真正的可移植性问题是：TM4C、MSPM0 同为 Cortex-M，CMSIS 写法可以沿用；**AM26x 的 Cortex-R5F 没有 NVIC，也没有 PRIMASK/BASEPRI**（靠 CPSR 屏蔽中断），这份实现在那里不存在，临界区必须进 OS 契约、实现放 platform（§5.7、§5.8）。
- **时基绑 DWT**：`Port/Time.c:36-60` 用 Cortex-M7 DWT/CYCCNT；`ZeroRateBiasObserver.hpp:41` 默认 tick 频率硬编码 480 MHz。Cortex-M0+ 没有 DWT，Cortex-R 要用 PMU 周期计数器，时基实现必须留在 port。
- **RTOS 双栈混用**：任务层同时用 `cmsis_os2` 与 FreeRTOS 原生 `uxTaskGetStackHighWaterMark`（`TaskManager.cpp:8,211`），无 OS 抽象层。
- **启动权在生成区**：`main.c:134-141` 调 `Port_Init`/`Application_Init`；`freertos.c:114` 调 `Application_InitRtos`；`freertos.c:139-143` 每 1 ms 调 `Application_Start`。换板 = 重接生成文件。
- **CMSIS-DSP 链接但未使用**：工程链接 `arm_cortexM7lfsp_math`，但项目代码无 `arm_*` 引用，`.map` 中无相应符号（仅 archive 载入行）→ 可移除。

## 3. 对提案的拆解与判定

### 3.1 提案原文（评审对象）

> app 做业务层，按兵种划分，后续可通过 cmake 快速切换编译；config 为装配根，按机器人划分，根据不同的兵种所具有的能力分配，被 app 所依赖。platform 为平台层，按厂商和开发板分，存放 cubemx 生成文件和手写的能力适配层。src 则为一个通用框架，里面存放公共的 bsp 层，被内部的 driver 等调用，还有 topic 架构以及一些算法库、小组件等。另有 test、tool、docs。

### 3.2 逐目录职责判定

| 目录 | 应回答的问题 | MUST 依赖 | MUST NOT 依赖 |
|---|---|---|---|
| `app/` | 一类**能力/行为**怎么实现（imu/chassis/gimbal/remote/link/launch） | `src` 的契约与公共库；本层 `app/common` | `platform` 实现/生成区；`config/assembly`；其他能力的内部实现（跨能力只经 msg/契约） |
| `config/` | 一台**具体机器人**用哪些能力、什么参数、装在哪块板 | `app`（assembly 链接）；`platform/board`（板能力） | 实现算法/协议/驱动；`profile` 不得 include 任何代码头 |
| `platform/` | 某块板如何把契约落到 HAL/寄存器；CubeMX 生成了什么 | `src/hal`、`src/hal/os` 契约；厂商 HAL/FreeRTOS/USB/CMSIS | `app`、`config` 的任何头（boot 契约除外）；把 HAL 类型放入公共头 |
| `src/` | 与产品和板都无关的通用框架（契约/算法/设备/消息） | 层内白名单（见 §5.7）；标准库 | `platform` 实现、`app`、`config`、RTOS/HAL 头（`hal/os` 契约除外） |
| `test/` | 契约与行为是否可脱离硬件验证 | 被测 target + `platform/mock` + ctest | 真实 port/生成区；**不得进入固件链接图** |
| `tool/` | 烧录/调试/生成/检查怎么做 | 无构建期依赖 | 不得成为固件构建的必需步骤；不得被 gitignore |
| `docs/` | 分层判据、决策、证据链 | 无 | 不得与代码/CI 规则不一致 |

### 3.3 必须修正的四处边界

#### M1 `config` 的双重身份会造成构建环

- **问题**：提案同时要求"`config` 是装配根"（要链接 `app`）与"`config` 被 `app` 依赖"（`app` 要 include `config`）。在 CMake target 依赖图上，同一 target 既被 `app` 依赖又依赖 `app` ⇒ **环**。【v0.3 校正】CMake 允许 STATIC 库之间循环依赖（会在链接行上重复出现），所以不一定在 configure 期报错；问题在架构层面：环一旦存在，就会被 INTERFACE/OBJECT 绕成"看起来能编"的隐式环，也无法再保证 app 能脱离具体机器人单独编译。
- **后果**：`app` 无法在没有机器人配置时单独编译/宿主测试；配置与实现的单一真源被破坏；换 profile 时无法判断改哪一边。
- **建议规则**：把 `config` 拆成两个 target：
  - `foray_profile_<profile>`：**INTERFACE 叶子**，只含生成头（能力集合、参数常量、板卡 ID），不 link 任何 target；
  - `foray_assembly_<profile>`：**STATIC 组合根**（`config/assembly/`），负责任务表、对象构造、启动入口、参数注入，只被最终 executable link；
  - `app` 只依赖 `foray_profile`（若允许）或完全不依赖 profile（推荐：参数由 assembly 注入）；`app` **绝不**依赖 assembly。
- **验收**：`cmake --graphviz` 生成的 target 图中不存在经过 `app → profile → assembly → app` 的环；把任意一个 profile 换成 `test_profile`，`app` 与 `src` 的源码零改动即可编译。

#### M2 `app` 按兵种划分会导致复制分叉

- **事实**：现有 `Application/` 实际上就是按**能力**长的（`Task/0_imu`、`1_chassis`、`2_gimbal`、`4_communication`），兵种差异并不存在于代码结构；真正"换车必改"的是 **4 个 app 文件**（§2.5 表 #1–#4；另有第 5 处板级 CMake，Dji 映射边界待裁决）。兵种间共享 IMU 姿态估计、云台模块、底盘控制器等大部分代码。
- **后果**：按 `app/infantry`、`app/hero` 建目录后，同一能力必然出现多份副本：一个 bug 要修 N 份、参数/接口漂移、review 无法判断哪份权威；config 的"能力分配"也失去意义（因为代码已经按兵种复制了）。
- **建议规则**：
  - `app` 一级目录使用**能力/角色白名单**（imu/chassis/gimbal/remote/link/launch/common/tasks/debug_comm）；
  - **兵种（branch，建议代码/doc 改用 `robot_type` 以免与 git branch 混淆）是 profile 的属性，机器人（robot）是 profile 实例**；新兵种 = 既有能力的重新组合 + 参数差异；新行为 = 新增 capability，而不是复制目录；
  - 能力用**链接期 target 组合**表达：每个能力一个 STATIC 库，`assembly` 按 profile 的能力列表 `target_link_libraries`；禁止 `#if FORAY_*` 出现在 `app/src`，禁止 `includes.h + USE_XXX` 宏开关模式（RM 社区已有反面案例）。
- **验收**：新增一个兵种 profile 时 `git diff --stat` 只触及 `config/profiles/`（+ 需要时一个 preset）；CI 检查 `app` 一级目录 ∈ 白名单。

#### M3 `src/bsp` 一词两义，且缺 os/boot 契约（v0.4 修订）

- **事实**：`src/bsp/hardware/` 下 7 个占位 `.hpp` 与现有 `Platform/Interface/*.hpp` 一一对应。传统 BSP = Board Support Package（板级实现），而提案又用 `platform/*/bsp_impl` 表示手写实现——同一个词同时指契约与实现。【v0.4 撤回】v0.1–v0.3 认为骨架"缺了 `Detail/*.h` 对应的 C ABI 一半"；项目主语言是 C++，契约统一用 C++ 头即可（§5.11），骨架只放 C++ 头的方向是对的。
- **后果**：①名称歧义会长期消耗评审时间；②缺 os/boot 契约时，临界区、时基与启动入口会继续散落在 PortKit、Port 与生成区里；③`bsp` 目录容易变成"什么都往里放"的垃圾桶；④PortKit（CMSIS/PRIMASK）若被当作"公共框架"搬进 src，会污染平台无关层。
- **建议规则**：
  - `src/hal/`：C++ 契约（`can.hpp … usb_cdc.hpp`，由 port 直接实现）+ `src/hal/os/`（最小 OS 契约，见 Q10）；现有 `Detail/*.h` 在 P2 暂放 `src/hal/detail/`，P3a 并入 C++ 契约后删除（§5.11）；
  - `src/boot/`：启动契约（见 M4）；
  - `platform/<vendor>/<mcu>/<board>/` 拆 `cubemx/`（生成物）、`port/`（手写实现，P3a 起为 C++）、`board/`（pinmap、时钟、能力清单、bring-up）；
  - `bsp` 一词只保留给 `platform/*/board/`（若保留），不再出现在 src；PortKit 的队列/通知进 `src/utils/`，临界区契约进 `src/hal/os/`，其 CMSIS 实现留在 platform。
- **验收**：P3a 后 `src/hal/detail/` 不存在；宿主测试只链接 `src/hal`/`src/lib`/`platform/mock` 即可编过；`src/**` 中 grep 不到 `cmsis`、`HAL_`、`FreeRTOS`、`stm32`。

#### M4 平台契约是"本机器人能力集" + CubeMX 生成区接缝需收口

- **事实 A（生成区接缝）**：`Core/Src/main.c:37` 与 `Core/Src/freertos.c:29` include `Application/Entry.h`，并在 USER CODE 区调 `Application_Init/InitRtos/Start`；`defaultTask` 承载应用周期。生成区与手写区在物理上同目录，靠 USER CODE 区与人工纪律维持。【v0.3 校正严重度】USER CODE 区本来就是 CubeMX 官方的扩展点，再生成时会保留；`Application/Entry.h` 已经是只依赖 `stdbool.h` 的纯 C 三函数启动契约（`extern "C"`）。所以这里的问题是"生成区直接引用了 app 目录路径，且由 `defaultTask` 承载应用周期"，修正方式主要是把它改名移到 `src/boot`、实现移到 `config/assembly`，工作量小，不构成开工前的阻断项。
- **事实 B（第二个破口）**：UsbCdc 生成代码与 Port 私有 ABI 双向直连（§2.3 缺口 2），不能按"接口/实现"直接切。边界方案见 **Q8**。
- **事实 C（能力枚举）**：`Gpio::Pin`（Power24V1/Power24V0/Power5V/UserKey/IMU CS/INT，共 8 脚）、`Spi::Device`（ImuAccelerometer/ImuGyroscope/AddressableLed）、`Uart::Endpoint`（RemoteReceiver/DebugConsole）、`Pwm::Channel`（Buzzer/ImuHeater）、CAN 固定 3 通道——都是 DM_MC02 的逻辑资源；Interface 与 Detail 双份写死。原样搬进 `src` 共享契约后，F407/TI 只有两条路：设备并集污染，或每板一份契约使 app 绑板。
- **建议规则**：
  1. `platform/**/cubemx/**` 只放生成物（Core/Drivers/Middlewares/USB_DEVICE/*.ioc/startup/.ld），手写代码 0 个；`port/`、`board/` 在物理上分开；CODEOWNERS + 生成清单 sha256 校验保证再生成不覆盖手写（不必在 CI 中安装 CubeMX；有 CubeMX 的 runner 时可加 regenerate-diff）。
  2. 引入 **boot ABI**：`src/boot/foray_boot.h` 用 `extern "C"` 声明 `foray_boot_init / foray_boot_init_rtos / foray_boot_run`（头文件可被生成区的 C 文件 include，实现写在 C++ 里；由现有 `Application/Entry.h` 演进；`InitRtos` 只在 RTOS 构建中调用，裸机构建只用 `Init` + `Run`）；生成文件只调这三个符号，**不再 include app 头**；`foray_boot_init` 内部先调 board bring-up（原 `Port_Init`）再装配对象（样例见 §5.6）。
  3. **板能力清单**：board 声明该板"提供哪些能力/资源"，profile 声明机器人"需要哪些能力"，校验 `robot_requires ⊆ board_provides`，缺失即编译失败（而不是靠运行期 `IsReady` 糊过去）。【v0.3】v1 用 board 头中的 `constexpr` 能力常量 + assembly 中的 `static_assert` 实现即可；`board.cmake` 形式的 configure 期清单作为可选增强，在 F407 接入（P3a）时视需要落地。
  4. **契约分两层**：`src/hal` 只保留通用总线/时基/存储等资源型契约（不枚举板级逻辑设备）；板级逻辑资源由 `platform/*/board` 声明、port 映射；若驱动需要绑定具体实例，在 `config/assembly` 装配期完成。【v0.3 细化】采用轻量做法：公共契约头只定义 API 和不透明的设备 ID 类型；具体 ID 常量由 `platform/*/board` 的头文件提供；驱动通过 `Config` 接收 ID，由 assembly 注入。改动面已实测：驱动中写死逻辑设备的只有 6 个文件、16 处（BMI088 的 4 个文件、Buzzer、WS2812）；CAN 通道已在 `Libraries` 中有 10 处以参数形式传入，有现成先例。不做 Zephyr 式的通用资源模型。
  5. **链接脚本冻结 + overlay**：CubeMX 生成的 `.ld` 不手改；自定义段（如 `.dma_buffer.imu_diag`）放到 `platform/.../board/link/overlay.ld`，作为第二个 `-T` 追加；CI 验证"再生成后段仍在、`.bin` 不变"。方案待 Q9 确认。
- **验收**：删除/替换任一生成文件后，`git grep "Application/" platform/**/cubemx` 为空；一个"空 app"骨架（只有 boot ABI）可单独构建并点亮板；换一块能力更少的 mock 板时编译期能报出缺失能力；再生成后 overlay 段仍存在。

### 3.4 提案缺失的必需物

1. **根 CMake 与 presets**：当前骨架没有任何构建文件；没有 root target 模型就没有"层"。
2. **宿主测试 + `platform/mock`**：契约层的可替换性必须能被验证；历史 Tests 可从 `fd1edbb` 恢复。
3. **CI 架构门禁**：include/依赖方向、生成区、禁止 GLOB、vendor 哈希、手写协议检查；规则不机器化必然回潮。
4. **`src/boot`、`src/third_party`、`platform/mock`、板能力清单、`docs/ai/architecture.md`**：分别对应启动接缝、foray_interfaces 生成头、宿主可测性、多板能力校验、唯一人读的分层判据。
5. **组织合规件**：`.foray-layer`、`CODEOWNERS`、CI（与五件套一起构成仓库规范）。
6. **框架可复用的保证（v0.3）**：最小 OS 契约（临界区 + 时基）、`src/utils` 并发原语、框架独立构建与裸机构建的 CI 检查（§5.8、§5.9）。

### 3.5 提案中正确的部分（先说优点）

- 四块切分与"装配根"直觉正确，直接命中现有"装配知识分散 + 生成区破界 + 构建无边界 + 测试缺失"四个痛点。
- `platform` 按厂商/开发板分层并物理隔离生成区，是解决 CubeMX 再生成与多板复用的正确方向。
- `src` 收拢通用框架（含算法、组件、topic）符合"可宿主编译、跨产品复用"的目标。
- `test/tool/docs` 一级化，正确对应"测试/工具/证据链必须入库"的教训。
- 与行业实践一致：Zephyr 的 board/SoC/driver 分离、ESP-IDF 的组件 PRIVATE/PUBLIC 依赖、XRobot 的"配置生成装配代码"都印证了同一方向。

### 5.2 CMake target 依赖图（目标态，完整）

```text
EXECUTABLE  foray_firmware_<profile>
 ├─ STATIC       foray_assembly_<profile>        config/assembly（组合根：任务表/对象构造/boot 实现）
 │   ├─ INTERFACE foray_profile_<profile>        config/profiles（纯数据生成头，叶子，无依赖）
 │   ├─ INTERFACE foray_boot                     src/boot（C 兼容的启动契约头，extern "C"）
 │   ├─ STATIC    foray_app_<capability>         app/<capability>（可选集合由 profile 决定）
 │   │   ├─ INTERFACE/STATIC foray_app_common

 │   │   ├─ INTERFACE foray_utils                src/utils（零平台小工具）

 │   └─ OBJECT    foray_board_<board>            platform/<vendor>/<mcu>/<board>/board（OBJECT，见图例）
 └─ OBJECT       foray_port_<board>              platform/.../port（用 C++ 实现 foray_hal 与 foray_hal_os；PRIVATE 依赖 vendor；OBJECT，见图例）
     ├─ OBJECT   foray_mx_generated_<board>      cubemx/ 生成物（Core/USB_DEVICE/Middlewares）
     ├─ OBJECT   foray_rtos_<board>
     └─ OBJECT   foray_usb_<board>

宿主测试（不交叉编译）：
EXECUTABLE foray_test_<name>  →  被测 target + STATIC foray_platform_mock + ctest

框架独立构建 / 裸机构建检查（v0.3，CI）：
只配置 src/ + platform/mock，不含 app/、config/，不提供任何 RTOS 头 → 全部框架 target 编译通过
```

图例（依赖方向 = 箭头指向被依赖方）：

- **只有最终 executable 可以 link `foray_assembly_*`**；库与测试不得 link assembly。
- `foray_os_freertos_<board>` 是 INTERFACE（只暴露头/宏），不是实现库；FreeRTOS 的实现（OBJECT）只链入 `foray_port_<board>`。迁移期任务外壳可以继续通过这些头用 `cmsis_os2`；【v0.3】终态任务外壳改用 FreeRTOS 原生 API（AM26x 的 TI SDK 不提供 CMSIS-RTOS2【推断，AM26x 启动时核实】，见 Q12），线程不进框架。
- `foray_platform_mock` 用 C++ 实现 `foray_hal` 与 `foray_hal_os`，仅供宿主测试；它不属于 `src` 的依赖，而是测试替身。
- **port 与 board 用 OBJECT 库，不用 STATIC【v0.3 新增】**：port 中有覆盖 HAL 弱符号的回调（`Can.c:462`、`Gpio.c:73`、`Spi.c:659/671/691`、`Uart.c:348/371/419`）。静态库里的目标文件只有在存在未解析引用时才会被链接器拉入；某个回调将来如果单独成文件，就会被静默丢弃，中断回调退化成 HAL 的空实现。OBJECT 库保证全部目标文件进入链接；也可以用 CMake 3.24+ 的 `$<LINK_LIBRARY:WHOLE_ARCHIVE,...>`。
- **C 链接只出现在三处**（v0.4，§5.11）：生成区调用的启动入口、覆盖 HAL 弱符号的回调、生成区里的中断入口；其余全部是 C++。

### 5.3 依赖规则（建议纳入 CI，机器可验）

**执行方式（v0.3 补充）**：每个 target 用 PRIVATE include 之后，规则 1–8 的大部分由 CMake 本身保证（看不到的头就 include 不了）。CI 只需补三类检查：target 依赖图断言、文本模式扫描（`file(GLOB)`、`#if FORAY_`、手写帧/CRC、原子读改写）、生成区与 vendor 哈希。不必为每条 include 方向单独写 grep 规则。

1. `app` 不得 link/看见 `foray_port_*`、`foray_board_*`、`foray_mx_generated_*`、`foray_rtos_*`、`foray_usb_*`、`foray_assembly_*`。
2. `src` **源码**不得 include/link `platform` 实现；`src` 的**宿主测试**可以链接 `platform/mock`（mock 只实现 ABI，不构成 src 对 platform 的依赖）；`src` 必须能只靠 mock 在宿主机构建。
3. `src/hal` 头文件（含 `os/`）不得出现 `stm32`、`cmsis`、`HAL_`、`FreeRTOS`、`cmsis_os2`，只允许标准库头；契约类型只用 enum class、POD 结构与不透明 ID/句柄，不暴露厂商或 RTOS 类型。【v0.4 修订：不再有 `src/hal/abi`】
4. `config/profiles/**` 不得 include 任何工程头；`profile` 是叶子。
5. `foray_assembly_*` 是组合根：**只有最终 executable 可以 link 它**；任何库/测试不得 link；任何头不得被 assembly 之外的 target include（boot 头除外）。
6. `test` 不得 link `foray_port_*`/`foray_board_*`/`foray_assembly_*` 的真实实现；测试二进制不得进入固件链接图。
7. `platform/**/cubemx/**` 不得出现 `app/`、`config/`、`Application/` 的 include；只允许 boot/board 契约头。
8. 禁止 `file(GLOB)` 收集业务源码；禁止全局 `include_directories()`；每 target 用 PRIVATE/PUBLIC/INTERFACE 显式声明。
9. `app/src` 中禁止 `#if.*FORAY_`（能力裁剪用 target 组合）；`#if` 只允许出现在生成头与 platform 适配层。
10. 只有 `app/tasks`、`app/common` 与 `config/assembly` 允许 include RTOS 头（经 `foray_os_freertos_<board>` INTERFACE）：迁移期可用 `cmsis_os2.h`，终态改用 FreeRTOS 原生 API（Q12）。`app/<capability>` 业务模块与整个 `src/` 零 RTOS；`src/` 需要临界区或时间时，只经 `foray_hal_os` 最小契约。【v0.3 修订】
11. 链路协议只允许来自 vendored `lower_link.hpp`（版本 + sha256 固定）；禁止在 `app/src` 出现手写帧/CRC。
12. `app` 一级目录白名单、`src` 一级目录白名单、`platform` 一级目录白名单；新增需 `decision.md` 登记。
13. （v0.3）框架代码（`src/`）不直接使用 `std::atomic` 的读改写操作（`fetch_*`、`exchange`、`compare_exchange_*`），一律使用 `src/utils` 的并发原语。原因：Cortex-M0+ 没有独占访问指令，这类操作做不到无锁（§5.8）。
14. （v0.3）框架代码开启 `-Wdouble-promotion`；豁免清单只含 IMU 姿态解算中有意使用 double 的文件（§5.10），新增豁免需在 `decision.md` 登记。
15. （v0.3）框架（`src/`、`platform/`、`cmake/`）不得引用产品（`app/`、`config/`）的任何路径或 target；框架必须能独立配置和构建（§5.9）。
16. （v0.4）C 链接（`extern "C"`）只允许出现在 §5.11 列出的三处；覆盖 HAL 弱符号的 `.cpp` 必须 include 对应的 HAL 头，让回调继承 C 链接；CI 用 `nm` 检查这些回调符号没有被 C++ 改名。

### 5.4 唯一开关与 presets 矩阵

- **唯一命令行开关：`-DFORAY_PROFILE=<profile>`**；板卡、能力集合、参数全部来自 `config/profiles/<profile>/profile.cmake`。
- 常用 preset：`arm-debug`（默认 profile × board_dm × Debug）、`arm-release`、`host-tests`；其他兵种/板在 CI 用显式 `-B` 目录展开（`cmake --preset` 的 binaryDir 不能引用 cache 变量，不要试图一个 preset 打天下）。
- 工具链进 `cmake/toolchains/`：首批 `arm-gcc-cortex-m7`、`arm-gcc-cortex-m4f`、`host`；按需增加 `arm-gcc-cortex-r5` / `tiarmclang-cortex-r5`（AM26x，Q13）与 `arm-gcc-cortex-m0plus`（MSPM0，P5）。GNU 专属选项（`--specs=nano.specs`、`-Wl,--wrap=`、GNU 链接脚本语法）只能出现在工具链或平台 CMake 中【v0.3】。本机路径进 `CMakeUserPresets.json`（不入库），CI 用环境变量。
- 现有两个构建期开关（`IMU_ENABLE_DIAGNOSTICS`、`IMU_GYRO_BANDWIDTH`，§2.4）在 P3b 收进 profile，不再作为独立 cache 变量。
- 生成 `foray_profile.hpp`（能力常量 + profile id + 源文件 hash + git describe），供装配/诊断/测试断言；app 不直接 include。
- 能力常量用 `constexpr` 而非宏；能力开关不生成 `#define FORAY_CAP_*`，而是决定 assembly 链接哪些能力库。
- **`config/profiles/<profile>/profile.cmake` 与生成头是唯一命名**（避免 `robot.cmake`/`profile.hpp.in` 的多套叫法）；`<profile>` 是 profile 名（如 `infantry_v1`），板卡是其属性而非独立维度。

### 5.5 能力模型与最小契约样例

- **机器人需求 vs 板能力**：profile 声明 `FORAY_FEATURES`；board 声明 `BOARD_PROVIDES`；校验 `robot_requires ⊆ board_provides`（v1 用 board 头的 `constexpr` 常量 + assembly 的 `static_assert`；下方 `board.cmake` 形式的 configure 期清单是可选增强，见 M4 规则 3）。
- **能力 = target**：`foray_app_<capability>`；assembly 只链接 profile 列出的能力。未链接的能力不会进镜像（含其全局对象）。
- **模块内差异**：用 `constexpr bool` / 依赖注入 / 非虚接口表达，不用预处理分支。
- **新兵种**：既有能力重组合 + profile 参数；**新行为**才新增 capability 库。新板才新增 platform board。

最小样例（仅示意 schema，P1 定稿）：

```cmake
# config/profiles/infantry_v1/profile.cmake（纯数据，不含源文件）
set(FORAY_PROFILE_ID infantry_v1)
set(FORAY_BOARD_VENDOR st)
set(FORAY_BOARD stm32h7/board_dm)
set(FORAY_FEATURES imu chassis gimbal remote)
set(FORAY_PARAM_CHASSIS_WHEELS 4)   # 参数按能力分组，具体 key 在 P1 定稿
```

### 5.7 `src` 层内依赖、topic 与 OS 抽象

**层内依赖（文字定义，避免箭头歧义）**

| 子层 | 允许依赖 | 禁止依赖 |
|---|---|---|
| `hal` / `hal_os` / `boot` | 标准库 | 其他层、OS、厂商头 |
| `lib`（纯算法/组件） | 标准库、`lib` 内部 | `hal`、`driver`、`msg`、OS |
| `utils` | 标准库 | `hal`、`lib`、`driver`、OS |
| `driver`（设备/设备协议） | `hal`、`lib`、驱动内协议 | `msg`、OS、`app` |
| `msg` | `utils`、`hal_os` 契约（如用临界区） | `driver`、`app` |
| `middleware` | `msg`、`hal`、`lib`；链路适配可依赖 `driver` | `app` |
| `app/<capability>` | `lib`、`driver`、`msg`、`middleware`、`hal` | OS（任务外壳除外）、`platform` 实现、`config/assembly` |
| `app/tasks`、`app/common` | 上面全部 + `foray_os_freertos`（迁移期） | `platform` 实现、`config/assembly` |

- **先把既有债裁决掉**：`ImuBodyMapping` 的 Device 反向依赖（改成 POD 入参或迁到 `src/driver/imu/`）；Device→Algorithm/Protocol 的合法下行依赖写入文档。否则搬进 src 只是复制债务。
- **topic 第一版不引入**：`src/msg` v1 只提供最新值邮箱/SPSC 队列（以 PortKit 队列、`ImuDataReadyMailbox`，以及 `RemoteReceiver`/`DjiMotor` 中的序号快照写法为基础通用化；架构图里的 `LatestValueMailbox` 不在 `a2cfd16` 中）；topic 在 P3b 后按需引入。【v0.3】能力拆成 target 后彼此不能 include，所以 msg v1 必须和 P3b 的能力拆分同步落地。最小 topic 规范：固定 POD、静态表、编译期 ID、`Peek()`（零拷贝，接受覆盖语义）与 `Take()`（拷贝）分离、ISR 只 publish、每 topic pub/drop 计数、禁止总线级 RPC、禁止运行时自动发现；1 kHz 控制 + 500–625 µs IMU 的实时预算先算清。
- **OS 抽象（Q10，v0.3 修订）**：建立**最小 OS 契约实体**，只含临界区（C++ RAII 守卫：构造时关中断并保存状态，析构时恢复，比 enter/exit 配对更不容易漏掉恢复）与单调时基（tick 与频率），可选再加忙等延时；实现放在 `platform/*/port`。理由：AM26x 的 Cortex-R 没有 PRIMASK/BASEPRI，MSPM0 裸机没有 RTOS，现有 PortKit 实现在这两处都不可用。**线程、队列、事件不进框架**：它们只出现在产品层（`app/tasks`、`config/assembly`），RM 固件用 FreeRTOS 原生 API，小项目用主循环 + 定时器中断。现有任务层的 RTOS 调用约 15 处（`osThreadNew`、`osThreadFlagsSet/Wait`、`osDelay`、`osKernelGetState`、`osThreadExit`、`osThreadGetId`，以及 1 处原生 `uxTaskGetStackHighWaterMark`），改成原生 API 的工作量很小。v0.2 的推荐（只留占位、继续直用 CMSIS-RTOS2）在 AM26x 与裸机前提下不再成立。

### 5.8 平台可移植性约束（v0.3 新增）

| 平台 | 内核 | 硬件双精度 | 无锁原子读改写 | 周期计数器 | 中断屏蔽 | RTOS | 编译器 |
|---|---|---|---|---|---|---|---|
| STM32H723（DM-MC02） | Cortex-M7 | 有（`__ARM_FP`=14） | 有 | DWT | PRIMASK / BASEPRI | FreeRTOS | GCC |
| STM32F407（C 板） | Cortex-M4F | **无**（`__ARM_FP`=4，double 走软件库） | 有 | DWT | PRIMASK / BASEPRI | FreeRTOS | GCC |
| TM4C | Cortex-M4F | **无** | 有 | DWT（按型号确认） | PRIMASK / BASEPRI | FreeRTOS（Q12 默认） | GCC |
| AM26x | Cortex-R5F | GCC 按 `vfpv3-d16` 编译为硬件双精度（`__ARM_FP`=12）；具体型号的 FPU 配置需对照数据手册 | 有 | PMU（无 DWT） | **CPSR I/F 位（无 NVIC、PRIMASK、BASEPRI）** | FreeRTOS（Q12 默认） | GCC 和/或 TI Arm Clang（Q13） |
| MSPM0 | Cortex-M0+ | **无 FPU** | **无**（实测编译失败） | 无 DWT | 仅 PRIMASK | 裸机（已确认） | GCC |

实测结论（方法见附录 F）：

1. **M0+ 不支持无锁原子读改写**：`static_assert(std::atomic<std::uint32_t>::is_always_lock_free)` 在 `-mcpu=cortex-m0plus` 下编译失败。现有代码中依赖无锁原子的有：`Libraries` 的 3 个文件（`DjiMotor`、`AxisController`、`Bmi088Transfer`）与 `Application` 的 3 个文件（`RemoteReceiver`、`ImuDataReadyMailbox`、`ImuTask`）。对策：规则 13 + `src/utils` 并发原语（计数器、最新值邮箱、单生产者单消费者环形队列；在 M4/M7/R5 上用 `std::atomic`，在 M0+ 上退回临界区实现）。现有 6 个文件在 P3b 迁移，不必为此提前改动。
2. **M4F 上 double 走软件库**：double 乘、除、加全部编译为 `__aeabi_dmul` / `__aeabi_ddiv` / `__aeabi_dadd` 调用；M7、R5（`vfpv3-d16`）为硬件指令。对策见 §5.10。
3. **Cortex-R 上 PortKit 临界区不可用**：对策是最小 OS 契约（§5.7）。
4. **框架的裸机基础已经具备**：`Libraries` 零 RTOS 调用、零堆分配（两处 `std::function` 字样都在"不使用"的注释里）。
5. **双编译器差异【推断】**：若 AM26x 采用 TI Arm Clang，代码需同时通过 GCC 与 Clang；`-Wl,--wrap=` 在 TI 链接器上是否可用需验证；链接脚本格式不同（TI 链接器用 `.cmd`）；CI 要多一套编译器。这些差异全部收进工具链与平台 CMake（§5.4），在 AM26x 启动时处理。

### 5.9 框架与产品的边界（v0.3 新增，Q15）

- **划分**：框架 = `src/` + `platform/` + `cmake/` + 框架自己的测试；产品 = `app/` + `config/`（本仓的 RM 下位机固件）。规则 2、15 保证框架不引用产品。
- **同仓开发，暂不拆仓**：单人维护两个仓库、两套 CI 不划算。第一个小项目真正启动时（P5），用 `git subtree split` 把框架提成独立仓库并保留历史；小项目与本仓都通过 submodule 或 `FetchContent` 引用框架。
- **框架必须能独立构建、能裸机构建**：CI 增加一个只含 `src/` + `platform/mock`、不提供任何 RTOS 头的构建配置，持续证明框架可以单独拿走（§5.2）。
- **框架只收至少两个产品真正共用的东西**：RM 专用的能力（底盘、云台、发射）留在 `app/`；不为尚未出现的小项目预先抽象。MSPM0 的 port 到 P5 才做；现阶段只守住三条几乎零成本的规则：`src/` 零 RTOS、不直接用原子读改写、全部静态分配。

### 5.10 浮点精度策略（v0.3 新增，Q14 已确认）

**现状【事实】**：反汇编 `a2cfd16` 的 Release ELF，执行双精度运算的函数集中在 IMU 姿态解算：

| 函数 | 内容 | 调用频率 |
|---|---|---|
| `Vqf::UpdateGyroscope` | 陀螺积分，调用 double `sin`/`cos` | 每个陀螺样本，2000 Hz（532 Hz 带宽配置；116 Hz 配置下为 1000 Hz） |
| `Vqf::UpdateAccelerometer` | 加速度计修正与零偏估计，调用 double `acos`，使用 double 的 `Matrix3` 与巴特沃斯低通（Release 中 118 条双精度相关指令） | 每个加速度计样本，1600 Hz |
| `GyroBiasCalibration` | 标定累加 | 只在标定窗口内 |
| `Vqf::Init`、`ButterworthLowPass::Init` | 系数计算（double `tan`） | 初始化时一次 |
| `Vqf::GetState` 等 | 诊断输出 | 低频 |

- 底盘、云台控制、PID 与电机驱动全部是 float。`ZeroRateBiasObserver` 源码里有 double，但没有调用者，未链接进固件。
- **这是有意设计**：`ButterworthLowPass.hpp:19` 注明状态与系数用 double，是因为 float 在长时间运行下会出数值问题（沿用上游 VQF 的结论）；`Matrix3` 是为零偏估计专门做的 double 版本，与 float 的通用矩阵并存。因此"全部改成 float"不是首选。
- **double 没有扩散**：对 Application 与 Libraries 的全部 36 个编译单元加 `-Wdouble-promotion` 做语法检查，只有 `Vqf.cpp` 报 18 处，都是有意的 double 运算。
- **接口是 float**：`Vqf` 的输入输出与 `AttitudeEstimator::Output` 都是 float；只有 `Vqf::InternalState` 诊断结构含 4 个 double 字段，外部没有使用。将来调整只是 IMU 能力内部的局部改动。

**决议（负责人确认）**：先按 H723 开发，双精度暂不处理。

**两道防护**（P3a 落地）：

1. 框架代码默认开启 `-Wdouble-promotion`，IMU 姿态解算文件豁免（规则 14），防止 double 在其他地方悄悄扩散。
2. `Vqf.cpp` 增加编译期检查，目标没有双精度 FPU 时直接报错，让"真正需要处理的时候"在第一次编译时暴露，而不是上板后才发现 CPU 占用异常：

```cpp
#if defined(__arm__) && (!defined(__ARM_FP) || !(__ARM_FP & 0x8))
#error "Vqf 内部使用 double，本目标没有双精度 FPU：先实测耗时或改用混合精度版本"
#endif
```

`__ARM_FP` 的第 3 位（0x8）表示硬件双精度；加 `__arm__` 条件是为了不影响宿主机测试。

**触发条件与届时的做法**：第一个要在 M4F 板（F407、TM4C）上链接 IMU 姿态解算能力的 profile 出现时处理。先用 DWT 实测两个更新函数的耗时；若超出预算，优先改成混合精度（热路径的三角函数与逐样本运算改 float，低通状态与累加器保留 double），并用 `test/data` 中的 IMU 基准数据在宿主机上对照姿态与零偏输出；仍不够再按标量类型做模板。P3a 的 F407 契约验证不需要 VQF：F407 验证 profile 不链接姿态解算能力即可（能力 = target）。

### 5.11 契约语言：C++ 为主，C 只用于外部强制的接缝（v0.4 新增，Q17）

**现状【事实】**（`wc -l` 原始行数，含空行与注释，与 §2.1 的统计口径不同）：手写代码约 18,600 行，其中 C++ 约 15,100 行（约 81%）；C 约 3,500 行，全部在平台接缝上——`Platform/Interface/Detail/*.h`（C ABI，778 行）、PortKit（194 行）、`Port/*.c`（2,470 行）、`Application/Entry.h`（47 行）。`Libraries` 下的 `.h` 文件实际都是 C++。

**C ABI 层的成本**：

- 枚举定义两份（§2.3 缺口 3），例如 `Can.hpp:19` 与 `Detail/Can.h:28`；
- C++ 门面基本是逐个函数转发加类型转换（`Can.hpp` 中的 `ToPortChannel`、`ToSendResult` 等）；
- port 用不上 enum class、constexpr、命名空间与 RAII；P3a 的设备 ID 注入在 C 里只能传整数。

**当初选 C 的理由，在 C++ 中都可以不靠 C ABI 实现**：

- 宿主测试打桩：链接期替换对 C++ 的非内联自由函数同样有效，mock 提供同名定义即可；
- 调用厂商 C 代码：STM32 HAL、TI SDK 的头文件都带 `extern "C"`，C++ 可以直接 include；
- 跨编译器 ABI 稳定：每次构建只用一个编译器（GCC 或 TI Arm Clang），不会混链两者的目标文件。

**必须用 C 链接的只有三处（外部强制）**：

| # | 位置 | 原因 | 写法 |
|---|---|---|---|
| 1 | 生成区调用的启动入口 `foray_boot_*` | `main.c`、`freertos.c` 是 C 文件 | `src/boot/foray_boot.h` 用 `extern "C"` 声明，实现写在 `config/assembly` 的 C++ 里（现有 `Entry.h` + `Entry.cpp` 已是这种写法） |
| 2 | 覆盖 HAL 弱符号的回调 `HAL_*Callback` | HAL 按 C 符号名调用 | 写在 port 的 `.cpp` 里，并 include 对应 HAL 头，让定义继承头文件中声明的 C 链接 |
| 3 | 中断入口 `*_IRQHandler` | 向量表按 C 符号名引用 | 保持在生成区的 C 文件里，不动 |

第 2 处是 C++ port 最需要防的坑：覆盖回调的 `.cpp` 如果没有 include HAL 头，编出来的是 C++ 改名后的符号，HAL 的弱实现照旧生效，编译和链接都不报错，外设回调静默失效。对策：规则 16 + CI 用 `nm` 检查这些回调符号没有被改名（风险 R18）。

**决议（Q17，负责人已确认）**：

1. 契约统一用 C++：`src/hal/*.hpp` 直接作为 port 要实现的接口（enum class、POD 结构、非虚自由函数），取消 `src/hal/abi`，枚举只定义一份。
2. port、PortKit 剩余部分与 `platform/mock` 改用 C++ 实现，直接 include 厂商头。
3. 最小 OS 契约用 C++ 写成 RAII 临界区守卫（§5.7）。
4. 沿用现有的嵌入式 C++ 约束：C++17、`-fno-rtti -fno-exceptions -fno-threadsafe-statics`、无堆分配、热路径不用虚函数（迁移源 0 处虚函数）。

**时机**：P1–P2.5 不改（不改行为的阶段，C 文件原样搬，`Detail/*.h` 暂放 `src/hal/detail/`）。P3a 本来就要重做契约（设备 ID 注入），在那时合并 C ABI 层、把 port 与 PortKit 改写为 C++（约 2,700 行），历史测试中的 C ABI 桩同步改为 C++ mock。转换注意点：`Spi.c`、`Uart.c` 用了 C++17 不支持的指定初始化器（GCC 作为扩展接受，`-pedantic` 下报警），需要改写；C 中 `void *` 的隐式转换在 C++ 里要显式写出。P3a 工时因此增加约 3–5 人日。

**其他平台**：TI Arm Clang 支持 C++17。MSPM0 裸机跑 C++ 时，需要确认启动文件会调用全局构造函数（`__libc_init_array`），否则全局对象不会被初始化（P5 检查项，风险 R19）。

- P0.5：① 一次性格式化手写代码（`legacy/` 下的 Application、Libraries、Platform/Interface、PortKit、Port；CubeMX 生成区与厂商代码用 `.clang-format-ignore` 排除），顺带把手写文件的行尾统一为 LF；② 用 `clang-tidy --fix` 把 C++ 标识符改为新命名，手工补齐模板、宏等工具改不到的地方，同步更新测试与调试脚本中的符号名；③ 格式化与改名分成不同提交，提交号写入 `.git-blame-ignore-revs`，让 `git blame` 跳过它们。
- P2：搬迁时文件名同时改为 snake_case，头文件保护宏随新路径更新。
- P3a：合并 C ABI、改写 port 时直接按新规则命名。
- CI：组织模板的 lint-c 会对仓库里全部 C/C++ 文件运行 `clang-format --dry-run --Werror`，必须排除生成区与厂商代码，否则数千个 HAL 文件会检查失败；命名检查在 P0.5 之后加入 CI。

**P0.5 的验收**：同工具链下 `.bin` 的 SHA-256 与 P0 复现的基线一致（格式化不改变生成代码；改名只改变符号名，按输入顺序布局时镜像预计也不变【推断】）。若改名使 SHA 变化，以函数大小集合一致为准，并逐项说明原因；宿主测试全绿。

**注意**：按符号名读存档的调试脚本（如读取 `stackHealthArchive`）在改名后要同步更新（风险 R20）。

## 7. 迁移方案

### 7.1 原则

1. 先有可对照的基线（构建 + 测试），再搬目录；**搬迁不改行为**。
2. 每个阶段可构建、可回滚、有量化对照（`.bin`/`.map`/`ctest`）。
3. 结构迁移与"丢失进度恢复"分开立项。
4. 保留 git 历史与 `git log --follow`；不空目录重写。
5. 1:1 的整目录/整文件搬迁与"混合文件拆分"分成两个阶段（P2 / P2.5），避免把"纯机械操作"与"需要设计判断的操作"混在一个 PR。
6. （v0.3）先改接口、后改行为：P3a 只调整框架接口（设备 ID 注入、OS 契约、并发原语），行为保持不变，用宿主测试与实机对照；P3b 才允许改行为。
