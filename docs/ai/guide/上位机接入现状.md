# 上位机接入现状（RoboLink v0.2）

## 1. 链路

USB CDC 虚拟串口，纯字节流，没有额外的 USB 包边界。解析要容忍半帧、粘包、一次读多帧。MCU 不发任何非 RoboLink 数据。

## 2. 帧

```text
14 B 帧头 + N × (6 B 槽位头 + 载荷) + 4 B CRC-32
```

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0..1 | Magic | `D3 91` |
| 2 | Version | `0x02` |
| 3 | Flags | bit0 ACK_PRESENT；bit1 KEEPALIVE（零槽保活） |
| 4..5 | Length | 整帧字节数，含帧头与 CRC |
| 6..7 | Sequence | 每帧 +1，u16 回绕，仅用于丢帧检测，不重传 |
| 8..11 | Timestamp | MCU 发送时刻，u32 µs，约 71.6 min 回绕 |
| 12 | Slot Count | 0 只允许保活帧 |
| 13 | Reserved | 0 |

槽位头 6 B：`type(u8) + flags(u8) + message_seq(u16) + payload_length(u16)`。CRC-32/ISO-HDLC（zlib 同款）覆盖 Magic 到 CRC 前，线上小端。MCU 单帧上限 **96 B**；一次可含多个槽位，必须全部解析。

解析顺序：找 `D3 91` → 等满 14 B 帧头 → 校验版本/长度/Reserved → 等满整帧 → 校验 CRC → 遍历槽位。任一步失败从候选头的下一字节重扫；CRC 错丢整帧并计数。

## 3. 握手（必须）

1. PC 先发 **HELLO**（26 B）：

| 偏移 | 字段 | PC 填 |
|---|---|---|
| 0 | proto_ver_major | `2` |
| 1 | proto_ver_minor | `0` |
| 2 | device_type | `1`（PC） |
| 3..5 | fw_version | 可填 0 |
| 6..9 | git_short | 0 |
| 10..17 | capabilities | **至少包含 0x30（bit 48）**；建议同时含 0x10。不含 0x30 时 MCU 不发姿态 |
| 18..19 | heartbeat_period_ms | 20 |
| 20..21 | max_frame_bytes | 512（至少 96） |
| 22..25 | device_id_digest | 0 |

2. MCU 在**同一帧**里回 `HELLO_ACK`（8 B）+ 本端 `HELLO`（26 B）。`HELLO_ACK.status == 0` 即握手成功；`acked_msg_seq` 是 PC 的 HELLO 序号。PC 不需要再确认 MCU 的 HELLO（当前 MCU 不等）。
3. 没收到 ACK 就每约 200 ms 重发 HELLO；`status` 1/2 表示版本或能力不匹配，检查 `capabilities` 是否含 0x30（和 0x10）、proto major 是否为 2。
4. 进入 READY 时双方 Frame Sequence 与全部 Message Seq 归零；重连后不要拿旧序号比较。
5. 握手后 PC 每 **20–50 ms** 发一个零槽保活帧（KEEPALIVE），或 HEARTBEAT。MCU 500 ms 收不到任何合法帧就停发姿态/状态；只监听、不发帧会看起来“连上但没数据”。

`HELLO_ACK` 8 B：`acked_msg_seq(u16)`、`negotiated_major(u8)`、`status(u8)`、`heartbeat_period_ms(u16)`、`reserved(u16)=0`。

## 4. 上传消息

| Type | 名称 | 载荷 | 频率 | 说明 |
|---|---|---|---|---|
| 0x30 | GIMBAL_ATTITUDE | 36 B | 约 1 kHz（实测 996 Hz） | 主要数据；PC 声明 0x30 才发 |
| 0x10 | SYSTEM_STATUS | 28 B 核心 / +24 B 诊断 | 200 Hz；诊断 1 s 一次 | 28 或 52 B 都要接受 |
| 0x02+0x01 | HELLO_ACK + HELLO | 8 + 26 B | 握手时 | 同一帧两个槽位 |
| — | 零槽保活 | 0 B | 20 ms 没发东西时 | Frame Flags 的 KEEPALIVE |

当前版本 MCU **不发 ACK、ERROR、HEARTBEAT 消息**。

### GIMBAL_ATTITUDE（36 B）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0..3 | u32 | sample_time_us | IMU 采样时刻，与帧头 Timestamp 同一 MCU 时钟 |
| 4..19 | 4×f32 | q_w, q_x, q_y, q_z | 云台系 → 世界系，标量在前 |
| 20..31 | 3×f32 | gyro_x/y/z | 云台系 rad/s，已扣零偏 |
| 32 | u8 | imu_state | 0 SETTLING，1 READY，2 DEGRADED |
| 33 | u8 | flags | bit0 = ATTITUDE_VALID |
| 34..35 | u16 | reserved | 0 |

欧拉角：`yaw = atan2(2(q_w q_z + q_x q_y), 1 − 2(q_y² + q_z²))`，`pitch = asin(2(q_w q_y − q_z q_x))`；yaw 左转为正，pitch 低头为正。

### SYSTEM_STATUS（28 B 核心）

| 偏移 | 字段 | 说明 |
|---|---|---|
| 0..3 | uptime_ms | MCU 开机时长 |
| 4 | mode | 7 = IDLE（当前第一版固定） |
| 5 | control_source | 0 = NONE |
| 6 | safety_state | 当前第一版恒 0（未收到快照），不要据此判断链路 |
| 7 | reserved | 0 |
| 8..11 | last_rx_control_seq | PC 发过快照时会前进 |
| 12..15 | last_accepted_control_seq | 当前第一版恒 0 |
| 16..19 | last_applied_control_seq | 当前第一版恒 0 |
| 20..21 | control_msg_age_ms | 当前第一版恒 65535 |
| 22 | link_state | 0 断开、1 USB、2 READY、3 ACTIVE |
| 23 | reserved | 0 |
| 24..27 | fault_flags | 0 = 无故障 |

诊断尾部 24 B（偏移 28..51）：`rx_frames(u32)`、`tx_frames(u32)`、`crc_errors(u32)`、`rx_overflow(u16)`、`tx_busy_drop(u16)`、`queue_drop(u16)`、`event_queue_depth(u8)`、`reserved(u8)`、`reserved_wide(u32)`。按“载荷长度 ≥ 52”判断是否存在，不能要求正好 28。

## 5. 当前实际行为（容易踩）

- **`link_state=ACTIVE` ≠ IMU READY**。IMU 状态只在 `GIMBAL_ATTITUDE.imu_state`；姿态在 SETTLING 也照发。
- 当前板 READY 后静止 5 min 的 yaw 漂移实测 **-0.05°（-0.010 °/min）**；SETTLING 不保证，不能拿 SETTLING 的 yaw 做标定。
- **每次 MCU 复位都重新标定**，冷启动约 42 s；协议文档里“复位后沿用标定、约 0.2 s READY”当前**没有实现**。不要硬编码 30 s/0.2 s，等 `imu_state=READY`。热启动被加热器问题拖住时会更长。
- **yaw 零点在 READY（或 DEGRADED）那一刻取**，不是上电时。SETTLING 的 yaw 是未定零点的原始值，会漂；`ATTITUDE_VALID` 也可能为 1。上位机应在 READY 时作废世界系目标/缓存，把当时 yaw 当作 0。
- **控制快照只记账、不执行**：`mode`、`safety_state`、accepted/applied、age 的固定值如上；不要据此判断“PC 控制已生效”。
- **帧序号会跳**：MCU 不重传；PC 高频发快照时 `tx_busy_drop` 可到约 2%，帧序号不连续是正常，不要重连。
- **载荷可以更长**：按 Payload Length 截断读取，忽略末尾追加字段；不能因为长于协议长度整帧丢弃。
- **时间戳 32 位 µs 会回绕**；`sample_time_us` 与帧头 Timestamp 的差要用回绕安全差值。样本在 MCU 内的停留常态 < 2 ms。
- 帧内可能有多个槽位（握手、状态+姿态），解析器要遍历全部槽位，不能只取第一个。
