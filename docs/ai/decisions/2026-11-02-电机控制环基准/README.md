# 1 kHz 电机控制环基准（2026-11-02）

电机架构（Decision-20261102-03）的验收判据：重构前（M0）与重构后（M7）在同一块板、同一台电机、同样的任务表下，
三项都不劣于重构前：
- 单轮耗时；
- 周期抖动；
- 从收到反馈到下发指令的延迟。

本文记录 M0（重构前），M7 完成后补在后面。

## 测法

bringup 达妙电机检查（`bringup::DmCheck`）功能检查跑完、失能之后，追加 10 s 的 1 kHz 控制环：
- 电机使能；
- 每轮先让驱动收发（`DmMotor::process()`），再用 PD 保持起点位置（Kp 2 N·m/rad、Kd 0.05，限 0.5 N·m）；
- 算出的力矩暂存进驱动。

每轮记录：

| 项 | 怎么算 |
|---|---|
| 单轮耗时 | 本轮开始（任务运行器给的 now）→ 驱动收发、算 PD、指令暂存完 |
| 周期抖动 | 相邻两轮开始的间隔与 1 ms 之差的绝对值，另计间隔超过 1.1 ms 的轮数 |
| 反馈 → 下发延迟 | 算指令时所用反馈的接收时刻（`hal::Can::Frame::received_us`，Decision-20261102-04）→ 这条指令放进发送队列 |
| 反馈有多旧 | 算指令时，所用反馈已经收到多久 |

结果由 `tool/debug/bringup_probe.py` 不停核读出。

- 任务：`dm`，1 ms 周期，优先级 23。在它之上的有 IMU（28）、监视（26）、心跳（25，1 kHz）、CubeMX 默认任务（24）；在它之下的有 io（20）。
- 现在的驱动先暂存指令，下一轮 `process()` 才发出。所以延迟里有一整拍，这正是重构要去掉的。

## 固件

| 构建 | 提交 | `firmware_bringup_dm_mc02.bin` 的 sha256 |
|---|---|---|
| Debug（`-O0 -g3`） | `d1ee1b9`（`f3/motor-benchmark`） | `98c4c01acf1ba669…` |
| Release（`-Os -g0`） | `d1ee1b9` | `e9497325d1d7ba23…` |

- 两份固件都在负责人的工作区里构建。工作区里有负责人对 `dm_esc.hpp` 的未提交改动，只改了注释。
- 工具链（`cmake/toolchains/arm-gcc-common.cmake`）把 Release 的选项写成了 `-Os -g0`。CMake 缓存里显示的 `-O3 -DNDEBUG` 被它盖掉，不起作用。
- Release 没有调试信息，探测脚本读不出结构布局。做法：
  1. 从 `git archive d1ee1b9` 导出源码，只在这份副本里把 `-g0` 换成 `-g` 再构建；
  2. 确认 `.bin` 与正式 Release 逐字节相同（GCC 的 `-g` 不改变生成的代码）；
  3. 用这份 ELF 读结果（存档里的 `firmware_bringup_dm_mc02_with_debug_info.elf`）。
- 烧录前读整片 Flash：前 232,272 字节等于 `deff3ae`（上一次的 bringup），其后到 256 KiB 全为 0xFF，256 KiB 之后与 11-02 首次备份相同。

原始日志与固件：仓库外的 `foray_mcu_archive/2026-11-02_motor_benchmark/`（sha256 见 `SHA256SUMS`）。

## M0 结果（重构前）

| 项 | Debug | Release |
|---|---|---|
| 轮数 / `dm` 任务错过周期 | 10001 / 0 | 10000 / 0 |
| 单轮耗时 平均 / 最长 | 36.3 / 272 µs | 11.2 / 92 µs |
| 周期抖动最大 | 308 µs | 139 µs |
| 间隔超过 1.1 ms 的轮数 | 1071（10.7%） | 7 |
| 反馈 → 下发延迟 平均 / 最长 | 1750 / 2060 µs | 1753 / 1893 µs |
| 用到的反馈最旧 | 1060 µs | 893 µs |
| 各任务单轮最长：IMU / 监视 / 心跳 / io / dm | 127 / 240 / 252 / 338 / 276 µs | 45 / 69 / 78 / 104 / 98 µs |

同一次运行里，达妙电机的功能检查（核对、使能、转动、通讯超时保护、失能保活、CAN1 收发）在两种构建下都通过。

**读法**：

- 延迟约 1.75 ms，与构建无关，是结构造成的。达妙电机一问一答：
  - 这一轮发出的帧，应答约 0.25 ms 后收到（由平均延迟反推：指令发出时距离它所用的反馈，隔了 2 个周期减去一次往返，2 − 1.75 = 0.25 ms）；
  - 到下一轮开始时，这份反馈已经约 0.75 ms 了；
  - 下一轮取用它算出指令，指令却要再等一轮才发出。
  重构后收 → 算 → 发在同一轮里完成，预期延迟约 0.75 ms 加单轮耗时，即约 0.76 ms。
- 单轮耗时：Release 平均 11 µs，只占 1 ms 的约 1%；最长值里含被更高优先级任务抢占的时间。
- 抖动主要来自比 `dm` 优先级高的任务，Debug 下它们更慢。真正的控制任务应排在 IMU 之下的最高优先级。这是任务表的配置问题，与电机结构无关；M7 沿用同样的任务表，才能对比。
- 位置保持误差为 0：PD 的力矩小于减速箱静摩擦，电机不动。这一项只用来确认控制环在跑，不评价控制效果。

探测脚本原先把"有间隔超过 1.1 ms"判为基准失败，太严。改为"跑满轮数且 `dm` 任务没有错过周期"，抖动只报告。
