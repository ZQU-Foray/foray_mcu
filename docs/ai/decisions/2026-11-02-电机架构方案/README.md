# 电机架构方案（Proposed，2026-11-02）

> **状态**：Accepted（2026-11-02）：负责人同意第 5 节 D1–D9 全部按推荐。对应 decision.md 的 Decision-20261102-03。
> 实施时有两处调整：M1 提前到 M0 之前；型号目录按品牌分文件。见该决策。

## 0. 一页摘要

**要解决的问题**：电机品牌、型号多，现在的写法是"一个型号一个模板特化，一组电机独占一条总线"，管理麻烦，用法也不统一；
同时控制要稳定在 1 kHz，新结构不能让性能变差。

**方案**：能力只跟**关节（Joint）**打交道，品牌、型号、接线都是装配时的数据。

```text
能力（云台、底盘、发射……）       读关节状态、写关节指令；SI 单位；不知道品牌
        ↕ 同一个任务里直接读写（控制环不经 topic）
关节 Joint                       一台电机折算到机构上之后的状态 + 指令（含方向、外接传动、零点）
        ↕
品牌驱动（DjiMotor、DmMotor）    每条总线上每个品牌一个；各自的状态机与发送节拍
        ↕ 用协议层编解码（DjiEsc、DmEsc，不变）
CAN 总线 CanBus（每条总线一个）  独占接收，按帧 ID 分给登记的驱动；装配时检查 ID 冲突与总线负载
        ↕
hal::Can
```

**性能**：1 kHz 的瓶颈是 CAN 总线带宽和"收反馈 → 算 → 发指令"的延迟链，不是软件抽象。
新结构守住两条规则：控制环里不跨任务；装配时就检查总线负载。抽象层每周期的额外开销在微秒级（1 ms 预算的 1% 以内）。
并且用上板基准测试验收：新结构不劣于现在的写法。

**要你决定的 9 件事**（详见第 5 节，每项都有推荐）：

| # | 问题 | 推荐 |
|---|---|---|
| D1 | 关节指令支持哪些模式 | 力矩 + 电机内阻抗（MIT），型号支持才能用 |
| D2 | 控制计算放在哪个任务 | 各能力自己的任务，电机收发作为同一任务的 step |
| D3 | 一条总线能不能被多个任务共用 | 不能：一条总线只归一个任务 |
| D4 | 位置的含义 | 有绝对编码器的型号给绝对位置，其余从第一帧反馈起算 |
| D5 | 单位 | 关节层一律 SI：rad、rad/s、N·m |
| D6 | DJI 不同产品线能不能挂同一条总线 | 能，装配时检查 ID 冲突 |
| D7 | 安全（失控、急停、指令中断） | 集中处理：安全门能力 + 每个关节的指令超时 |
| D8 | 名字 | Joint（关节），与 ROS 2 的 ros2_control 一致 |
| D9 | CanBus 放在哪一层 | `src/driver/can_bus`：hal 契约不变 |

## 1. 现状与问题

现在的电机代码（`src/driver/motor/`）：

| 部件 | 作用 |
|---|---|
| `MotorGroup<型号, N>` | 能力持有的电机组：`init`、`process`、`enable`、`disable`、`set_torque`、`read_state` |
| `MotorAdapterFor<型号>` | 型号 → 品牌适配器的模板特化，装配品牌默认参数 |
| `MotorModel` 枚举 | M2006、M3508、GM6020_CURRENT、DM_J4310 |
| `MotorState` | 角度（度）、转速（rpm）、在线、有效、使能、故障 |
| `DjiMotor`、`DmMotor` | 品牌驱动，各自 `init()` 时用 `hal::Can::claim_receiver()` 独占一条总线的接收 |

问题：

1. **一条总线只能挂一组同型号电机**。RM 车上常见的接法做不到：CAN1 上同时挂底盘的 M3508 和拨弹的 M2006，分属两个能力；
   或者同一条总线上 DJI 与达妙混接。
2. **型号写在类型里**。能力拿到的是 `MotorGroup<M3508, 4>*`，换型号要改能力代码，或者把能力写成模板。
3. **加型号要改通用代码**：改枚举、写特化。品牌专有字段也进了通用结构（达妙的 `master_id` 在 `MotorConnection` 里）。
4. **只有力矩接口，单位沿用旧代码**（度、rpm）。达妙电机内的阻抗控制（MIT 的 Kp/Kd）用不上，今天的 bringup 检查只好绕过电机组直接用驱动。
5. **位置一律从第一帧反馈起算**。达妙和 GM6020 的绝对位置丢了，云台上电找零需要它。
6. **安全策略分散**：失控保护、急停，每个能力要自己写一遍。

现在改的代价最小：旧 app 已归档，电机组没有能力在用。只有宿主测试和 `lib/component/axis_controller` 的注释提到它。

## 2. 目标与不做的事

**目标**

- G1 用法统一：能力只用 `Joint`，与品牌、型号无关。
- G2 加型号只加一条数据，加品牌只加一个驱动。
- G3 一条总线上可以混接品牌、型号；装配时查出 ID 冲突。
- G4 1 kHz 控制不受影响：控制环零额外跨任务延迟；装配时检查总线负载；用实测验收。
- G5 安全集中：急停、失控、指令中断在一处处理。
- G6 宿主可测：mock CAN 加模拟电机，与今天的 `dm_fake_motor.hpp` 同一套路。
- G7 守住框架规则：驱动不碰 topic 与 RTOS；能力只有 `init`/`step`；无堆分配；热路径不用虚函数；不写 `#if`。

**不做**

- 运行时发现电机、热插拔。
- 达妙的位置速度模式、速度模式（见 D1）。
- 改 CAN 波特率或改用 CAN FD：要改 CubeMX 生成区。一条总线要挂 4 台以上达妙电机时再登记（见 4.2）。
- 上位机链路、参数在线调节。

## 3. 结构

### 3.1 协议层（不变）

`protocol::DjiEsc`、`protocol::DmEsc`：纯编解码，不碰硬件。

### 3.2 CAN 总线 `device::CanBus`（新增，`src/driver/can_bus/`）

- 每条物理总线一个对象。它是这条总线唯一的接收方（`claim_receiver()`），所以同一条总线上可以有多个驱动。
- 驱动在初始化时登记自己要收的帧 ID（单个 ID 或 ID 区间），连同一个处理函数（函数指针 + 上下文，与 `hal::Callback` 同一写法）。
- `receive(now)`：把接收队列取空，按帧 ID 查登记表，交给对应驱动。每帧一次间接调用。
- 发送不经过它：`hal::Can::send()` 本来就允许多方调用（port 用临界区保护硬件队列），各驱动直接发。
- 初始化检查：两个驱动登记的 ID 有重叠 → `init()` 失败。
- 统计：不认识的帧、各驱动收到的帧数。总线负载估算见 4.2。
- 它不只服务电机。超级电容、别的 CAN 外设以后也能登记到同一条总线上，所以放在 `src/driver/can_bus/`，不放在 `motor/` 下。

**不接电机的总线**（负责人 2026-11-02 问：简单兵种两路 CAN 够电机用，第三路拿去做别的，还适用吗）：

- 适用。`CanBus` 只管"按帧 ID 分给谁"，不知道电机，登记上来的可以是任何 CAN 设备的驱动。例如：
  - 超级电容控制板；
  - 与另一块板的板间通讯；
  - 只有一个设备的总线：也照样建一个 `CanBus`，只有一个登记项。
  这样驱动只有一种写法（登记到 `CanBus`），以后在这条总线上加设备，不用改已有的驱动。
- 想收下"没人登记的所有帧"的设备（总线记录器、协议转换），可以登记为兜底项。
- 第三路这台车根本不用：组合根不建它的 `CanBus`，什么都不占。
- 第三路的引脚改作别的外设（不再是 CAN）：那是 CubeMX 与 `board.hpp` 的事，`CAN_COUNT` 变成 2，框架不用改。
- 总线负载检查与 ID 冲突检查对非电机设备同样有效：每个登记项写明自己的帧 ID 与每秒帧数。
- 这条总线归哪个任务，按 D3 的规则：通常就是用这个设备的能力所在的任务（例如超级电容的功率管理，100 Hz）。

### 3.3 品牌驱动

现在的 `DjiMotor`、`DmMotor` 改造后保留，各自的状态机不变：DJI 合帧发送、多圈累计；达妙回读核对、清错使能、通讯超时。

- 构造时接收 `CanBus&` 与本总线上该品牌的关节表（关节指针 + 型号 + 接线）。
- `process()` 拆成两半：
  - 接收：由 `CanBus` 分发帧后更新关节状态；
  - `transmit(now)`：读关节指令、编码、发送。
- DJI 驱动支持同一总线上混接 C610、C620、GM6020（D6），初始化时检查 ID 冲突：
  - 反馈：C6x0 的 k 号是 0x200+k，GM6020 的 j 号是 0x204+j，k = j + 4 时冲突；
  - 控制：C6x0 的 5–8 号与 GM6020 电压模式的 1–4 号都用 0x1FF，含义不同，二者不能同时出现。GM6020 电流模式用 0x1FE/0x2FE，没有这个问题。

### 3.4 关节 `device::Joint`（新增，`src/driver/motor/joint.hpp`）

一台电机折算到机构上之后的状态与指令。能力只看到它。

```cpp
// 示意，字段以实现为准
struct JointState
{
    float position_rad;            // 机构位置：含方向、外接传动、零点偏移；绝对与否见型号目录
    float velocity_rad_per_second;
    float torque_newton_meter;     // 反馈力矩（DJI 由电流 × Kt 换算）
    float temperature_celsius;     // 没有温度反馈的型号为 NaN
    hal::os::Microseconds stamp_us; // 这份反馈收到的时刻（见第 6 节的接收时间戳）
    bool feedback_valid, online, enabled, fault;
    std::uint8_t fault_code;       // 品牌原始故障码（达妙的状态码），排查用
};

enum class JointMode : std::uint8_t
{
    TORQUE,    // 只给力矩：全部型号
    IMPEDANCE  // 电机内阻抗：τ = Kp(p* − p) + Kd(v* − v) + τff；只有支持的型号（达妙 MIT）
};

class Joint final
{
  public:
    const JointState &state() const;
    bool set_torque(float newton_meter);                      // 没使能、非有限值时返回 false
    bool set_impedance(float position_rad, float velocity_rad_per_second,
                       float stiffness, float damping, float torque_newton_meter); // 型号不支持时返回 false
    bool enable();  // 请求出力；达妙还在核对时返回 false
    void disable();
    bool supports(JointMode mode) const;
    float maximum_torque_newton_meter() const;
    // 驱动那一侧的接口（写状态、读指令）与能力分开，能力看不到
};
```

- 方向、外接传动比、零点偏移是**关节配置**（与机构有关），型号固有参数在型号目录里（与机构无关）。
- 指令带时间戳：`transmit()` 时发现指令超过 `command_timeout` 没有刷新，就按 0 力矩发，并记一次超时（D7）。

### 3.5 型号目录（新增，`src/driver/motor/catalog.hpp`）

每个型号一条 `constexpr` 数据，不再有通用枚举和模板特化：

```cpp
// 示意
namespace motor_catalog
{
inline constexpr DjiModel M3508{protocol::DjiEsc::c620(), 19.2F, /*Kt*/ 0.3F, /*满量程*/ 20.0F, /*绝对位置*/ false};
inline constexpr DjiModel GM6020_CURRENT{protocol::DjiEsc::gm6020_current(), 1.0F, 0.741F, 3.0F, true};
inline constexpr DmModel DM_J4310{DmMotor::Profile::j4310(), /*绝对位置*/ true, /*支持阻抗*/ true};
}
```

型号属于哪个品牌，由它的类型决定（`DjiModel` 只能交给 DJI 驱动），装错在编译期报错。

### 3.6 装配

- profile（`params.hpp`）写关节表，只含数据：
  - 型号；
  - 第几路 CAN（编号，不是板级句柄）；
  - 电调 ID 或 ESC_ID、MST_ID；
  - 方向、外接传动比、零点偏移。
- 组合根把编号换成 `board::CAN_n`，构造 `CanBus` 与品牌驱动，再把关节指针注入能力的 `Config`。
- 组合根里用 `static_assert` 检查每条总线的负载（4.2）。

```cpp
// 组合根示意：云台两台达妙电机在 CAN1，底盘四台 M3508 与拨弹 M2006 在 CAN2
device::Joint g_yaw, g_pitch, g_wheels[4], g_trigger;
device::CanBus g_can_1{board::CAN_1};
device::DmMotor g_can_1_dm{g_can_1, {{&g_yaw, params::YAW}, {&g_pitch, params::PITCH}}};
device::CanBus g_can_2{board::CAN_2};
device::DjiMotor g_can_2_dji{g_can_2, {{&g_wheels[0], params::WHEEL_M1}, /* ... */ {&g_trigger, params::TRIGGER}}};
static_assert(device::load_percent(params::CAN_1_JOINTS, 1000U) <= 80U, "CAN1 在 1 kHz 下超载");

void gimbal_receive(hal::os::Microseconds now) { g_can_1.receive(now); }
void gimbal_step(hal::os::Microseconds now) { g_gimbal.step(now); }
void gimbal_transmit(hal::os::Microseconds now) { g_can_1_dm.transmit(now); }

constexpr std::array<common::TaskSpec, 2> TASKS{{
    // 姿态一更新就算：收反馈 → 云台控制 → 发指令，同一个任务里按顺序
    {"gimbal", 1024U, 27U, common::on_topic(topics::imu::attitude, 2U), {gimbal_receive, gimbal_step, gimbal_transmit}},
    {"chassis", 1024U, 25U, common::every_ms(1U), {chassis_receive, chassis_step, launcher_step, chassis_transmit}},
}};
```

### 3.7 线程模型

- **一条总线只归一个任务**（D3）。这条总线的接收、所有驱动的发送，以及用这些电机的控制计算，都在这个任务里按 step 顺序执行。
  所以关节对象不需要跨任务同步，控制环里也没有 topic。
- 同一条总线上的两个能力（底盘、发射）放进同一个任务，各占一个 step（任务表每个任务最多 8 个 step）。
- 别的任务要看电机状态（遥测、上位机），由持有关节的能力把状态发布成 topic，它们订阅。topic 只出现在控制环以外。
- DM-MC02 有 3 路 CAN。云台单独一路、底盘与发射一路，还剩一路，按控制环分总线不难。

### 3.8 安全

- **使能**：能力在要出力时调用 `enable()`，之前的力矩指令都被拒绝（Decision-20261102-01 的约定不变）。达妙会先清错、再确认使能；DJI 电调没有使能命令，`enable()` 之后即接受力矩，没使能时照样发全零保活帧。
- **安全门**（D7，新增能力 `app/actuator`，step 排在发送之前）：
  - 订阅全局的"急停 / 失控"topic（由遥控、裁判系统等能力发布），有效时把它管的关节全部失能；
  - 统一检查每个关节的指令超时。
  它是能力，因为驱动不能订阅 topic（驱动不依赖 middleware），组合根又不能含行为（架构 §3.6）。
- **驱动自己的保护不变**：达妙写进 RAM 的通讯超时（今天上板验证过）、故障后撤销出力、离线后重新核对。

## 4. 性能

### 4.1 1 ms 里的 CPU 开销

- H723 主频 480 MHz，1 ms 约 48 万个时钟周期。
- 抽象层的代价（估算）：
  - 一次函数指针调用：几到十几个周期；
  - 拷贝一份关节状态（约 32 字节）：几十纳秒；
  - 查一次登记表：几个比较。
  4 台电机全算上，不到预算的 1%。
- 已有实测（都是 -O0 的 Debug 构建）：
  - 心跳 topic 发布到被读到：最长 9 µs（10-31）；
  - IMU 中断里发布到任务被叫醒：最长 90 µs（11-02）；
  - 今天 `dm` 任务的单轮最长 280 µs。这是墙钟时间，包含被 IMU 等更高优先级任务抢占的时间，不是驱动本身的开销。Release 构建还没测，由 M0 的基准补上。

### 4.2 CAN 总线负载（物理限制，与架构无关）

1 Mbps 下，一帧 8 字节标准帧连帧间隔约 111 位；位填充最坏再加约 24 位，即每帧 0.11–0.135 ms。

| 接法（控制 1 kHz） | 每毫秒的帧 | 负载 | 结论 |
|---|---|---|---|
| DJI 4 台（1 帧指令 + 4 帧反馈） | 5 | 56–68% | 可以 |
| DJI 8 台 | 10 | > 100% | 不行：DJI 反馈固定 1 kHz，与控制频率无关 |
| 达妙 1 台（今天实测：每秒放进发送队列约 1000 帧） | 2 | 22–27% | 可以 |
| 达妙 3 台 | 6 | 67–81% | 可以，余量小 |
| 达妙 4 台 | 8 | 89–108% | 不行；降到 500 Hz，或改 CAN FD |

- 装配时检查：按每条总线上的型号、台数与控制频率算负载，超过阈值（建议 80%）就 `static_assert` 失败，不必等到上车才发现跑不满 1 kHz。
- 计算按品牌给每周期帧数：
  - DJI：每 4 台一帧指令，加上每台固定 1 kHz 的反馈；
  - 达妙：每台每周期一帧指令加一帧反馈。
- 达妙电机支持 CAN FD（说明书：波特率超过 1 Mbps 时自动切换），板上的 FDCAN 也支持。以后需要时，这是扩容的路，要改 CubeMX 生成区，先登记。

### 4.3 延迟链

控制性能最容易被"好用的结构"拖累的地方：每多一个任务、多一次 topic 中转，周期没对齐时就可能多出最多 1 ms 的延迟和抖动。本方案的对策：

1. 控制环不跨任务（3.7）：收反馈 → 算 → 发指令在同一个任务里，中间没有排队。
2. 云台由 IMU topic 触发（`on_topic`，实测叫醒最长 90 µs），姿态一更新就算、马上发。也可以用 1 kHz 定时，由 profile 选。
3. 绑定在编译期完成：控制环里不查表、不按型号分支。帧分发查表在接收里做，每帧一次。
4. 每份反馈带收到的时刻，控制器按真实 dt 计算微分、做延迟补偿。
   - 达妙是一问一答：本周期发指令，反馈随后就到（估计 0.3 ms 内），下一周期开头取用；
   - DJI 反馈自己按 1 kHz 发，与控制周期不同步，相位会漂。
   有了时间戳，这两种情况控制器都知道数据有多旧。

### 4.4 基准测试与验收（M0、M7）

在 bringup 里加一个 1 kHz 控制环基准：收反馈 → 算一个 PID → 发指令，用 TIM2 的 µs 时基记录三项：
- 单轮耗时：平均与最长；
- 周期抖动：相邻两次开始的间隔与 1 ms 之差；
- 从收到反馈到指令放进发送队列的延迟。

Debug、Release 各测一次。重构前（M0，现在的驱动）与重构后（M7）对照：三项都不劣于重构前，才算验收通过。

## 5. 需要你决定的事

### D1 关节指令支持哪些模式

| 选项 | 说明 |
|---|---|
| A 只给力矩 | 最简单；达妙的电机内阻抗用不上，位置环全在单片机里算 |
| **B 力矩 + 电机内阻抗（推荐）** | 力矩全部型号都有；阻抗只给支持的型号（达妙 MIT），`supports()` 可查，装配时也能检查 |
| C 再加达妙的位置速度、速度模式 | 要切换电机的控制模式（写寄存器 0x0A）、换量程语义，核对与使能流程都要跟着变 |

推荐 B。MIT 的阻抗在电机内部按它自己测得的位置、速度计算，这个回路不经过 CAN，不受 1 kHz 通讯周期限制。所以比单片机里 1 kHz 的位置环更硬、响应更快，云台、关节类机构很需要。
C 的位置、速度控制用 MIT 的 Kp/Kd 也能做，代价不值得。

### D2 控制计算放在哪个任务

| 选项 | 说明 |
|---|---|
| **A 各能力自己的任务（推荐）** | 电机收发作为同一任务的 step，排在控制计算前后；零额外延迟 |
| B 集中的执行器任务 | 能力经 topic 下指令、读状态；多一个周期的延迟和抖动，topic 消息还受 64 字节上限 |

推荐 A，理由见 4.3。

### D3 一条总线能不能被多个任务共用

| 选项 | 说明 |
|---|---|
| **A 不能，一条总线只归一个任务（推荐）** | 简单，零同步；同一条总线上的几个能力放进同一个任务 |
| B 能 | 关节要跨任务同步，或者跨任务的部分经 topic，多一个周期延迟；容易在不知不觉间引入延迟 |

推荐 A。DM-MC02 有 3 路 CAN，按控制环分总线够用；真不够时，再按 B 单独登记。

### D4 位置的含义

| 选项 | 说明 |
|---|---|
| **A 有绝对编码器的给绝对位置（推荐）** | 达妙、GM6020 输出轴有绝对编码器，上电即知位置，云台可以直接找零；M3508、M2006 的编码器在减速箱前面，从第一帧反馈起算。型号目录标明是哪一种；关节配置可加零点偏移 |
| B 一律从第一帧反馈起算（现状） | 统一，但云台要另找办法得到绝对角 |

### D5 单位

| 选项 | 说明 |
|---|---|
| **A 关节层一律 SI：rad、rad/s、N·m（推荐）** | 与驱动、物理公式、ROS 2 一致，换算只在驱动里做一次 |
| B 维持度、rpm（现状） | 与旧代码的参数一致 |

选 A 的话，`lib/component/axis_controller`（现在是度、rpm）要改成 SI。按 Decision-20261027-01，迁移来的代码只当零件用，阶段 A 用到它时再改。

### D6 DJI 不同产品线能不能挂同一条总线

| 选项 | 说明 |
|---|---|
| **A 能，装配时检查 ID 冲突（推荐）** | 例如 C620 的 1–4 号与 GM6020 电流模式的 1–4 号可以共存（反馈 0x201–0x204 与 0x205–0x208，控制帧 0x200 与 0x1FE）；冲突规则见 3.3 |
| B 不能，一条总线一种产品线（现状） | 规则简单，但浪费总线 |

### D7 安全怎么做

| 选项 | 说明 |
|---|---|
| **A 集中（推荐）** | 安全门能力：急停 / 失控 topic 有效时全部失能。每个关节有指令超时：超时就按 0 力矩发，建议默认 3 个控制周期 |
| B 各能力自己处理 | 每个能力都要写一遍，容易漏 |

另外请定：急停后恢复，要不要人工确认（例如遥控拨杆回中再拨上）。推荐要。

### D8 名字

| 选项 | 说明 |
|---|---|
| **A Joint（关节）（推荐）** | 与 ROS 2 的 ros2_control（joint state / command）一致，上位机那边的人一看就懂；轮子也是关节 |
| B Actuator（执行器） | 含义准确，但与上位机的叫法不一致 |
| C 继续叫 Motor | 与"电机型号"混在一起，容易分不清"机构上的关节"和"那台电机" |

### D9 `CanBus` 放在哪一层

负责人 2026-11-02 问：能不能在 `src/hal` 里做。

| 选项 | 说明 |
|---|---|
| **A `src/driver/can_bus`，hal 契约不变（推荐）** | `hal::Can` 仍是"每条总线一个接收方、全收"，`CanBus` 是建在它上面的纯软件分发 |
| B 做进 hal 契约：`hal::Can` 支持多个接收方 | 各接收方登记 ID 过滤，各有一个接收队列；由每块板的 port 实现，可以用 FDCAN 的硬件过滤 |
| C 软件 `CanBus` 的代码放在 `src/hal` 目录里 | 和 A 相同的代码，只换了目录 |

推荐 A，理由：

1. **它不是硬件能力，是软件逻辑**。`src/hal` 只放契约，由每块板的 port 与 mock 实现（架构 §3.1）。
   - 按 B，分发逻辑要在每块板的 port 里各写一遍：DM-MC02、以后的 F407 C 板、MSPM0 等，mock 也要写一遍。
   - 按 A，只写一次，所有板共用。框架追求的是新板只写最少的 port。
2. **硬件过滤省不了什么**。1 Mbps 下一条总线最多约 7000–9000 帧/秒。软件查表每帧几十个时钟周期，加起来不到 480 MHz 的 0.1%。
   而且现在 CubeMX 里每路 FDCAN 只配了 1 个过滤器（全收）；要用硬件过滤得改生成区，以后每块新板也要配。
3. **多接收队列只有跨任务共用总线时才有用**。D3 推荐一条总线只归一个任务，用不上。
   真要跨任务，也可以在 A 的 `CanBus` 里给登记项加各自的队列，不必改契约。
4. **C 只是换个地方放，却破坏了"hal 只有契约"的约定**：
   - `hal` 现在是只有头文件的 target；
   - 依赖规则与 CI 检查都按"契约由 port 实现"来写。
   为一个目录位置改规则，不值得。
5. **为什么不放 `src/middleware`**：品牌驱动要登记到 `CanBus`，而驱动不能依赖 middleware（架构 §2.3）。所以它只能在驱动层或更低。

B 在一种情况下值得：以后某块板的 CAN 帧多到软件分发跟不上，或者必须在中断里就按 ID 分流。到时再单独登记，把多接收方加进契约。
A 的 `CanBus` 接口可以保持不变，只换底层实现。

## 6. 我按授权直接定的细节（你可以否决）

- `CanBus` 的分发用固定大小的登记表加函数指针，不用模板元组：组合根写法简单，开销是每帧一次间接调用。
- `hal::Can::Frame` 加接收时刻：port 在中断里把帧放进队列时写入 `hal::os::now_us()`，mock 同样处理。
  - 用途：关节状态的时间戳用它，延迟测量准确；
  - 还能修掉今天上板发现的问题：停发期间队列里的旧帧，会让离线判定晚一个 LINK_TIMEOUT。
  - 这是 hal 契约的变更，按惯例单独登记。
- 品牌驱动的 `process()` 拆成"由 CanBus 分发接收"与 `transmit(now)`。达妙的核对、使能状态机原样保留。
- 型号目录按品牌分类型（`DjiModel`、`DmModel`），不再有通用的 `MotorModel` 枚举。
- 迁移完成后删除 `MotorGroup`、`MotorAdapterFor`、`MotorModel`、`MotorConnection` 与对应的宿主测试，`brand_extension` 测试改为"新品牌驱动登记到 CanBus"。
- 总线负载检查用 `constexpr` 函数加组合根里的 `static_assert`。阈值 80% 写在 profile 里，可以改。
- bringup 的达妙电机检查改用 `Joint` 与新驱动，作为新结构的第一个上板用例。

## 8. 风险与代价

- 框架里多两个部件（`CanBus`、`Joint`）和一个能力（安全门），文档和测试都要跟上。
- DJI 混接的 ID 规则容易写漏，靠宿主测试把冲突组合列全。
- 关节状态要发布给别的能力时，受 topic 64 字节上限约束：一台一个 topic，或者只发需要的字段。
- 量化与摩擦：今天测得 DM-J4310 的摩擦约 0.2 N·m，小力矩控制要考虑。这与架构无关，阶段 A 整定时处理。
- 产品固件应当用 Release 构建。M0 会给出 Debug 与 Release 的差距，供你决定 bringup 以后用哪种。
