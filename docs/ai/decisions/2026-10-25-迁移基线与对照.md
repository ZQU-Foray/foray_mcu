## 4. 对照判据（v0.3 修订：按阶段区分）

1. **P0（在原结构上复现基线）**：同工具链、同提交、同构建选项下，`.bin` 的 SHA-256 应与基线一致；同时导出 `arm-none-eabi-nm -S --size-sort -C` 的符号表存档，作为后续阶段的对照基准。若 hash 不一致（常见原因：工具链小版本/路径/时间戳），记录差异原因，以段大小 + 符号表为准。
   **P0.5（格式与命名）**：仍要求 SHA-256 与 P0 复现结果一致；改名若使 SHA 变化，以函数大小集合一致为准，并逐项说明原因。
2. **P1、P2、P2.5（不改行为的结构调整）**：主判据是**符号名与大小集合一致**（同工具链、同编译选项下逐函数一致）；段大小作辅助，允许少量对齐填充差异。目标文件按 target 组织后链接顺序会变，`.text` 布局随之改变，**`.bin` 的 SHA 预计不再相同，不作判据**。
3. 允许的差异：文件路径字符串、调试信息、构建时间戳、链接顺序带来的地址变化；**不允许**：业务符号缺失/新增或大小变化（除结构性重命名，需逐项记录）。
4. **P3a（改接口不改行为）起**：符号集只作参考，**行为等价**由 host 测试（含 `test/data/` 的 IMU 基准数据）与实机对照证明；`.bin` 变化需归因。

## 7. P0 复现结果（2026-10-26）

> **更正（2026-10-26）**：本节初版写的"xPack 与原 Arm 官方 `gcc-15.2.rel1` 产物逐字节一致"不成立。Debug 镜像内含工具链安装路径（见下文），Debug SHA 能对上，说明 §2 的基线本来就是用本机同一路径下的 xPack 构建的；评估文档第 37、240 行也是这样记录的。Arm 官方 `gcc-15.2.rel1` 的产物从未与基线对照过。

**跨平台复现（Linux，2026-10-26）**：WSL Ubuntu 22.04 + xPack 15.2.1-1.1 linux-x64（发布包 SHA-256 `da6a49ad4003944b823c6c93702a8787c922ab34bd7e918ec0eaf6933a9b1ff6`）：

- **Release `.bin` 与基线逐字节一致**，CI 以此作为 P0–P0.5 的硬性闸门（`.github/workflows/ci.yml` 的 `firmware-legacy`）。
- **Debug `.bin` 不一致**：240,440 B，`.rodata` 多 2,120 B。原因是 `-O0` 下 libstdc++ 头文件（`<array>`、`bits/atomic_base.h`）的断言把 `__FILE__`，也就是工具链安装路径编进了镜像。Debug SHA 只在工具链装在完全相同的路径时才能复现，CI 对 Debug 只要求构建成功。
- 符号"名称 + 大小 + 类型"集合：两种配置都与基线一致，唯一差异是 `_sdata`。Linux 的 `nm -S` 显示其大小为 4，Windows 的 `nm` 不列出它，而 `readelf` 两边都是 0。此外大小相同的符号，两边 `nm --size-sort` 的排序也不同。**结论：`nm` 文本不能跨平台直接 diff**，P1 的符号对照工具要先归一化（例如基于 `readelf -sW`，只取 size > 0 的 FUNC/OBJECT，排序后比较）。
  - 【2026-10-26 P1 已解决】`tool/ci/symbols.py` 用 `readelf -sW` 归一化（有大小的函数与对象符号：名称、大小、类型、绑定、输出段），存档的符号表在 Windows xPack 与 Linux Arm GNU 两套工具链上逐项一致，见 [P1 构建骨架记录](2026-10-26-P1-构建骨架/README.md)。
