# RoboLink v0.2 对账记录（2026-11-03）

> Decision-20261103-01。本记录给出 MCU 端编解码与协议文本、PC 端实现三方核对的方法与结果；上板联调的结果在后续步骤补充。

## 1. 依据

| 项 | 版本 |
|---|---|
| 协议文本 | `foray_interfaces` `dev` @ `5973436`，`protocol/robolink.md`（v0.2） |
| PC 端实现 | `foray_platform` `dev` @ `de496bd`，`foray_platform/src/link/robolink_*.cpp` |
| 标准帧 | `test/data/robolink/golden_v0_2.txt`，37 个向量，由 `tool/robolink/make_golden.py` 生成 |

## 2. 方法

三份实现互相独立：

- **标准帧**：Python 生成器只照协议文本写，CRC 用 `zlib.crc32`，整数与浮点用 `struct` 的小端编码。生成前先自检：`zlib.crc32(b"123456789") == 0xCBF43926`（§1.3），各载荷长度等于协议表。
- **MCU 端**：`src/middleware/robolink`，宿主测试 `robolink_wire`、`robolink_messages` 逐字节对照标准帧。
- **PC 端**：`tool/robolink/pc_crosscheck.cpp` 链接 PC 端的编解码，对同一批标准帧。

向量覆盖：

- 合法帧：MCU → PC 的握手应答、状态与姿态同帧（94 B）、带诊断尾部的状态（76 B）、姿态无效；PC → MCU 的 HELLO（含没声明 0x30、主版本 1、心跳 0）、控制快照（含 §7.1 的末尾追加字段）、HEARTBEAT 槽、ACK、ERROR、HELLO_ACK；保活帧。浮点只用 float32 能精确表示的值。
- 消息内容应拒收的 5 个：控制快照的保留标志位、保留字段、生效子系统里的 NaN，HELLO 的设备类型越界，HELLO_ACK 的保留字段。
- 帧被拒的 17 个：CRC、版本、未知帧标志、保活位与槽位数矛盾、帧头保留字节、长度越界（17、513）、未注册类型、未知槽位标志、槽位标志与类不符、载荷过短、槽位越界、槽位数与内容不符、载荷超过 486 B、ACK_PRESENT 缺失或多余。

## 3. 结果

**MCU 端**：两项宿主测试通过。还覆盖了以下几种情况：

- 全部标准帧夹着垃圾字节（含假魔数），按 1、2、3、7、64、100、512、4096 字节分块喂给解析器，取出的帧正好是帧层合法的那些，顺序不变，各类计数与期望一致；
- 512 B 的最长帧逐字节喂入；
- 缓冲区末尾单独的 0xD3 保留到下一包；
- CRC 错的帧整帧丢弃，藏在它载荷里的合法帧不交出；
- 缓冲区满时只收下装得下的部分。

**故意改坏 12 处，测试都失败**：

- 保活位不置；
- 不查槽位的类；
- CRC 错只丢 1 字节；
- 不查 ACK_PRESENT；
- 不查帧长度上限；
- 丢掉末尾的 0xD3；
- 状态漏写 `control_msg_age_ms`；
- 姿态有效位不写；
- 不拒非有限浮点；
- 未使能子系统的字段不清零；
- 有效期提示不限 50 ms；
- 不查控制快照的保留字段。

其中"CRC 错只丢 1 字节"与"不查帧长度上限"是补了用例之后才被抓到的：一个是坏帧载荷里藏合法帧的用例；另一个原来会让测试卡死，补了"解析器总有空间收后续字节"的断言后直接报错。

**PC 端**（`pc_crosscheck`）：

| 核对项 | 结果 |
|---|---|
| 帧级接受与拒绝（36 个向量） | 与期望一致 |
| 字节流解析器取出的帧 | 29 帧，等于帧头与 CRC 合法的向量数 |
| MCU → PC：状态核心、诊断尾部、姿态、HELLO_ACK、MCU 的 HELLO 的字段 | 一致 |
| PC → MCU：PC 编出的控制快照、HELLO（与 `RoboLinkHostLink` 的取值相同）、保活帧 | 与标准帧逐字节相同 |

**差异 1 处**：

- 协议 §7.1 允许载荷末尾追加字段，旧接收方按 Payload Length 截断读取；
- PC 端的 `payload_size_matches()` 要求长度正好等于协议长度，所以拒收向量 `pc_control_extended`（56 B 的控制快照）；
- MCU 端按协议接受。

现在两端都只发协议长度的载荷，不影响联调。以后哪一端先追加字段，另一端就会整帧丢弃，需要算法组按 §7.1 改。

## 4. 握手的口径（协议没写死的地方）

PC 端评审文档第 3 条把"HELLO 由哪端发起"列为待确认。MCU 端按 PC 端现有代码配合，见 Decision-20261103-01 第 4 点：

- PC 发 HELLO；
- MCU 在同一帧里回 HELLO_ACK 与本端 HELLO，回 OK 即进入 READY；
- 随后发完整状态（带诊断尾部）。

标准帧 `mcu_handshake` 就是这一帧的格式，PC 端解码通过。
