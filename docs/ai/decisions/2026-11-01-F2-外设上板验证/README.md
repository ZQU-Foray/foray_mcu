### 首轮发现的问题（已修正，没有改变被测的框架代码）

首轮（`2b6c821`）17/20：三项没过，查下来都是测量方法的问题。

| 项 | 首轮读数 | 原因 | 处理 |
|---|---|---|---|
| （脚本无法运行） | OpenOCD 报 `invalid command name "0"` | 生成的 Tcl 把 `runner[0]` 的 `[0]` 当作命令替换 | 转义方括号（`dc8ae1b`） |
| 时基 | 每秒 1,020,104 | 速率按名义间隔 1 s 算，实际还包括读取本身的约 20 ms；heartbeat 1021 轮与 TIM2 的比例恰为 1 kHz | 速率改按 TIM2 走过的时间算，TIM2 用 OpenOCD 的主机毫秒数核对（`dc8ae1b`） |
| monitor | 收到 1020、发布 1021，丢失 0、乱序 0 | 两个计数在不同时刻读出 | 改为"最近序号减收到次数为 0 或 1、丢失 0、乱序 0"；结构按 32 位字读，字段不会读到一半（`dc8ae1b`） |
| IMU 延迟 | 每秒 43 次超过 200 µs，最大延迟 4294967294 µs | **bringup 能力的测量 bug**：用本轮开始的时刻减 topic 最近一次发布的时刻。中断每秒约 7400 次，任务醒来后、读 topic 前常有新发布，得到 −3～−6 µs，按无符号数成了约 42 亿 µs 并计入 late。SWD 采样 4000 次：没有一次真正超过 200 µs（中位 13 µs，最大 63 µs），负值 16 次 | `bringup.imu_event` 带上中断里发布的时刻，任务读到这一份后再取时刻相减；宿主测试补上这个情形，旧实现在此断言失败（`978bec1`） |

首轮 IMU 任务的等待超时累计 56 次，都发生在第一次读数之前（BMI088 初始化期间没有数据就绪中断，靠 1 ms 超时推进），稳态增量 0；次轮 0 次（复位前传感器已被首轮固件配置好，数据就绪中断一开就有）。

### 加热

| 阶段 | 读数 |

| 没接 24 V（复位后 29–210 s） | 加热器在预热状态，占空比 200‰；TIM3 PSC 239、ARR 9999、CCR4 2000、CH4 使能（100 Hz、20%），与代码一致。温度 37.1 → 40.6 ℃，接近板子自身发热的平衡点，加热电阻没有电源 |

### 指示（蜂鸣器、RGB 灯）

- 内存读数：指示状态 `IMU_RUNNING`；WS2812 的颜色数据在 (0,255,0) 与全灭之间约每 0.5 s 切换（亮度 32）；蜂鸣器两段音都已发出并停止（阶段 3）。

### monitor 的延迟

次轮 monitor 的最大延迟 249 µs，每秒约 19 次超过 100 µs（10-31 没有 IMU 时最大 9 µs）。任务表里 IMU（优先级 28）高于 monitor（26），IMU 单轮最长 113 µs，且可能连续几轮，monitor 等它们跑完属于设计预期；清单不判定这一项。

### SBUS（16:55 补测）

负责人接上 SBUS 接收机与遥控器后（板子随之重新上电）。探测：每秒 72 帧（SBUS 14 ms 一帧），1825 字节 / 73 帧 = 每帧 25 字节，拒收 0，丢字节 0；
UART 错误事件累计 2 次、失控帧累计 2978 帧，都发生在探测之前（接线、遥控器开机前），探测期间不增长。
随后用 SWD 每 0.2 s 读一次 `bringup.sbus` 的最新消息，共 60 s，负责人按提示操作（`sbus_interactive*.log`）：

| 时刻（复位后） | 操作 | 读数 |
|---|---|---|
| 244–270 s | 拨动摇杆 | 通道 1 在 321–1663、通道 2 在 329–1173、通道 5 在 321–1340 之间变化；丢帧 0、失控 0 |
| 270 s | 关遥控器 | 丢帧标志置 1 |
| 271 s | — | 失控标志置 1，通道变为接收机的失控预设（1024, 1024, 1, 1024）；帧计数照常增长（接收机继续发带标志的帧） |
| 288 s | 开遥控器 | 丢帧、失控都回到 0，通道恢复 |

### CAN（19:16 补测，固件 `8d66a34`）

负责人把一台 GM6020 接到板上丝印 CAN2 的口，电机由板上两路可控 24 V 输出供电。bringup 不碰这两路输出（`board::POWER_24V_0/1`，PC14、PC13，
CubeMX 初始化为低 = 关），这次经 SWD 写 `GPIOC_BSRR = 0x6000` 临时打开（高 = 开，复位后恢复关闭）。

- 第一次探测三路都是 0 帧：FDCAN 的协议状态为空闲、错误计数全 0，即线上没有任何信号——电机线脱落，负责人接回后正常。
  读 FDCAN 的 PSR / ECR 可以区分"没人发"（空闲、0 错误）与"波特率不对"（接收错误计数上涨），以后排查先看这两个寄存器。
- 接回后探测：CAN2 每秒 1002 帧（GM6020 的 1 kHz 反馈），标识符 0x205（ID 1 的 GM6020），`dji_feedback_seen` 只有 0x205 一位；
  软件丢帧 0、硬件丢帧 0、Bus-Off 0，收发错误计数 0；CAN1、CAN3 都是 0 帧——丝印 CAN2 对应 FDCAN2（`board::CAN_2`）。
- 读 FDCAN2 消息 RAM 里最近收到的帧，按 GM6020 反馈格式解码：角度 276（12.1°）、转速 0 rpm、转矩电流 −52～−70（零点附近）、温度 25 ℃，与静止、室温相符。
- GM6020 不需要先收到控制帧就会发反馈；bringup 只收不发，电机不会动。CAN 发送等阶段 A 的电机能力。

### USB CDC

- 枚举为 `0483:5740`（`/dev/serial/by-id/usb-STMicroelectronics_STM32_Virtual_ComPort_315F366D3233-if00`）。当前用户不在 `dialout` 组，负责人用 `setfacl` 临时放开。设备号不固定：16:55 重新接线后板子成了 `ttyACM0`、调试器成了 `ttyACM1`，按 by-id 路径找。
- 串口没打开时：`connected` 为 1，第一行卡在端点里，之后每秒跳过 10 行（与设计一致）。探测脚本原来只报"每秒 0 行"，已补上提示（`1a0b3f0`）。
- 打开串口（原始模式）读 3 s：28 行完整状态行，相邻两行的 `t=` 都相差 100 ms；发送 32 字节，原样回显。打开串口时边读边探测：每秒 10 行，跳过 0 次（探测 20/20，USB 一项由脚本判定）。
- 回显计数多出的 12 字节，就是打开串口之前卡住的那一行残片 `t=223036 hb=`：Linux 串口打开时默认开着回显，切到原始模式之前把它回显给了板子。用不切原始模式的方式（如直接 `cat`）打开会形成来回回显，要用 miniterm 之类的终端。
- 静止（板面倾斜约 11°）：加速度 (−0.50, 1.84, 9.53) m/s²，模长 9.72；四元数算出的横滚 10.9°、俯仰 2.8°，与加速度算出的 10.9°、2.9° 一致；温度 50.0 ℃；陀螺样本每秒 1994 个。
- 陀螺单样本的标准差 2.8 / 3.7 / 3.3 °/s（均值接近 0），比 BMI088 的规格噪声（约 0.3 °/s）大一个数量级。10-26 原固件在同一块板上的采集是 3.4 / 3.3 / 4.0 °/s（[采集记录](../../../../test/data/imu/2026_10_26_lost_fw_gyro_capture/README.md)），两者一致，不是新驱动带来的；当时归因于电机振动或驱动干扰。阶段 A 做零偏与噪声基准时，在电机与 24 V 断电的条件下另录。

## 结论

F2 验收的技术判据都已满足：bringup 固件在板上启动；任务按表运行（1 kHz 周期任务、按 topic 触发、中断触发）；中断里发布的 topic 叫醒阻塞等待的 IMU 任务，每秒约 6800 次，没有超时，最大延迟 73 µs；宿主测试 27/27。
F3 中已验证的驱动检查：SPI 读 BMI088、GPIO 外部中断、PWM（加热闭环）、SPI 发送（WS2812）、USB CDC 收发、UART 收 SBUS（含失控保护）、CAN 接收（GM6020 反馈）、时基。
F2、F3 的勾选留给负责人验收。
